Finalize the ordinary packaged Detcore preload after the outer Cargo build. This executable must never be called by a Cargo build script.

--prebuilt <so> stages an existing runtime file instead of the Cargo output, but only after the unchanged fixed build and qualification have run and the prebuilt bytes prove identical to the qualified artifact. Any other bytes are refused: this receipt attests the fixed liteinst-runtime build, and no second provenance can be recorded in it.

--buck qualifies a supplied Buck .so directly against Buck-declared sources and publishes the builder=buck2 receipt arm that ci/verify-packaged-detcore.py pins. This fbsource build compiles reverie-liteinst-artifact from the sibling //hermetic_infra/reverie target, which carries the Buck declared-content authority (resolve_buck / with_buck_build), so --buck runs that sequence here; the Hermit-pinned git build still refuses by name until a Reverie pin bump carries the authority there. Like the Cargo arm runs cargo, --buck runs the one pinned buck2 build itself, through the retained command runner with --show-full-output, and with_buck_build binds the runner’s own last retained record of that run — there is no command or digest parameter a caller could fill in: the ELF path is parsed from the retained buck2 stdout and its digest computed from the stdout-derived file inside with_buck_build (this process computes the same digest again only for the receipt). A context that cannot run buck2 — for example a Buck genrule action, which buck2 is already driving — cannot use this mode; the genrule keeps the Cargo --prebuilt gate and its by-name refusal instead. Still PLUMBING ONLY and unqualified: the D1c-2/D1c-6 machine-code recipes refuse the real Buck-built ELF by name inside qualification, and the fbcode profile does not yet deliver its pinned rustc flags to the closure (see require_profile_flags_applied), so no Buck receipt has ever been emitted.

require_profile_flags_applied 🔒
A receipt may list LITEINST_RUNTIME_RUSTC_FLAGS only when the supplied profile actually delivers them to the transitive closure. The profile .bzl states this as LITEINST_RUNTIME_FLAGS_APPLIED: the fbcode profile sets it False — fbcode_configured_alias transitions platform and constraints only, it has no rustc-flags parameter, and no fbcode build-mode constraint encodes this flag list (the Reverie authority also pins exactly the alias’s three constraints, so none can be added here) — while the OSS shim profile, whose toolchain select applies the list, sets it True. Checked at receipt publication, where the flags would be listed: anything but an explicit True refuses by name and no receipt is emitted.
