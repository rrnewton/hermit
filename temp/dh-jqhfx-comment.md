Investigation (musetrain, 2026-11-05): the wait is identified. xstate_probe::qualify() takes ProbeLock, a blocking flock(LOCK_EX) on the per-user temp file hermit-xinuse-probe-<uid>.lock with NO timeout, held across the whole Probe::run. Probe duration is contention-sensitive (calibration spins switched out, certificate retries up to MAX_ATTEMPTS=200 per trial, PMU counter reopens up to 5), so under 2 donor validations on one host one probe can hold the lock for tens of seconds while every other v3 process waits unbounded on flock; the donor checkouts have separate XDG caches, so the per-host cache cannot rescue the waiter, and the node per-test bound kills it at exit 124. Idle-host reproduction here (2 concurrent nextest jobs x 3 rounds, both tests, via temp/probe-concurrent.rs in the musetrain slot): all pass, 5.5-14.9s — donor-level load is needed to reproduce the timeout.

Does 4709 touch this code? No: the 4709 diff against hermit-cli/src/xstate_probe/ is empty, and the qualify/cache machinery predates it (issue 4515). 4709 only adds resolve_auto, so default-profile runs of v3-declaring guests reach host qualification more often than before (cached after the first). The two hanging tests name explicit x86-64-v3.

Proposed fix, after 4709 lands, as its own Test-plan change: bound the probe-lock wait (nonblocking try-lock poll with a deadline and cache recheck, then a named refusal) and/or bound total probe wall time, so lock hold and wait are both bounded; regression via a concurrent-qualification test or a lock-wait unit test.
