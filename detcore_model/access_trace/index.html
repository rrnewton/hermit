Module access_trace 

Source
Expand description

Record types of the access trace (--record-access-trace-to).

The access trace is a sidecar of a run that records its schedule. It says what each guest operation touched, keyed by the operation’s position in that schedule (the run’s own .events file), so a reader can line two runs up and name the conflicting operations whose order differs between them.

The file is JSON Lines: one TraceRecord per line, tagged by "kind". The first line is a TraceHeader. A run that finishes cleanly ends with a TraceEnd; a trace without one was cut short. A record is written when its last schedule event is recorded, so syscall records follow post; a call that never returned is written when its thread enters its next call, or at the end of the run. Readers sort by the index they need.

Every event index here is a position in the recorded schedule: the index the scheduler gave the event when it recorded it. Syscall records carry the thread’s own syscall count as nth, the unit of crate::happens_before::Position::SyscallCount, so (tid, nth) names the same operation in two runs of one program while its control flow agrees.

The trace observes; it never feeds back into the run. Nothing in these types is read by the scheduler.

Not recorded: some operations touch more than their records say.

  • splice and copy_file_range with a NULL offset move the file cursor, but record no cursor access;
  • poll, select, ppoll and the epoll waits record no access to the descriptors or channels they check;
  • path operations (unlink, rename, stat by path, the dirfd of the *at calls) record nothing;
  • FUTEX_WAIT_REQUEUE_PI records no access to its second futex word;
  • kill(-1) records nothing.
