pub const CPU_PROFILE_LONG_HELP: &str = "The CPU the guest sees: auto (the default), x86-64-v2, x86-64-v3, or host-no-rdrand. auto presents x86-64-v3 where the run and host qualify for it and x86-64-v2 everywhere else; name x86-64-v2 for a run whose CPU must not depend on the host. A run qualifies on the ptrace backend, with CPUID virtualized and no --gdbserver, on a host that passes the x86-64-v3 startup qualification (`hermit host-capabilities --cpu-profile x86-64-v3`); under a hypervisor auto presents x86-64-v2 without qualifying the host, and where a check that can change between runs takes x86-64-v3 away, the run\'s log says so; the choice is never printed on stderr, which the guest\'s output owns. auto also reads what the guest\'s executable and its program interpreter declare they need (GNU_PROPERTY_X86_ISA_1_NEEDED): a program declaring x86-64-v3 runs under it, admitted as an explicit x86-64-v3 is, or is refused (exit 122) where it cannot run; one declaring x86-64-v4, or one auto cannot read, is refused rather than guessed. `hermit record start` resolves auto by those declarations, so that the recording of a program that runs at x86-64-v2 does not depend on the host: x86-64-v2 unless one declares x86-64-v3. The exception is a program whose glibc C library (the libc.so.6 beside its program interpreter) declares x86-64-v3, which runs at x86-64-v2 on no host: record start presents x86-64-v3 for it where the recording and host qualify, as `hermit run` does, and x86-64-v2 elsewhere, where glibc refuses it. Hermit\'s library launch reads the declarations alone. The chosen profile and why are logged at debug level and written to the run\'s manifest, and a recording holds the profile; replays and reruns use it and never choose again. A later exec of an image needing more is refused where each exec is checked (the ptrace backend), never upgraded; KVM checks only the first image, so a later KVM exec gets no such refusal. Apart from that C library, auto reads no shared library: where only another library declares its need, name the profile. A named profile always means exactly itself. host-no-rdrand is available for `hermit run` on the ptrace backend with CPUID faulting and virtual time; it refuses hosts without CPUID faulting instead of allowing native CPUID. RDRAND and RDSEED are hidden. Check availability with `hermit host-capabilities --cpu-profile host-no-rdrand`. Recording and replay with host-no-rdrand are not supported.\n\nWith --cpu-profile host-no-rdrand, CPUID remains intercepted, but its answers come from the host CPU with hardware-randomness and unvirtualized timing features hidden. Results are host-CPU-model specific: cross-host builds need the same CPU model and compatible kernel/XSTATE settings and CPU topology. The tracer and guest are pinned to the lowest originally allowed CPU, even with the timeslice disabled; repeat runs require the same allowed CPU set. Host XSAVE behavior is retained without the x86-64-v3 XSTATE qualification, so programs inspecting XSAVE or signal-register metadata have no determinism guarantee. Programs must honor the advertised feature bits; unconditional RDRAND or RDSEED is not trapped by this profile.\n\nv3 is offered only on the ptrace backend, on hosts that pass a startup qualification (`hermit host-capabilities --cpu-profile x86-64-v3` runs it alone). A recording binds the host facts its guest\'s answers come from, and replay refuses a host where any of them differs (<https://github.com/rrnewton/hermit/issues/4243>).\n\nWith --cpu-profile x86-64-v3, Hermit checks at startup that this host does not change the XSTATE_BV bits a guest reads (with XSAVE, XSAVEC or XSAVEOPT, or in a signal frame) when the host saves and restores the guest\'s registers. The check samples a fixed set of cases and forces only CPUID exits, so a CPU or hypervisor that behaves differently only on other instruction paths, or on VM exits the guest cannot see, is not excluded. Firmware (SMM) entries cannot be checked at all. x86-64-v2 runs, including an auto run that chose x86-64-v2, are not affected.";
