agent-utils

Linux command-line tools and agent instructions for running several coding agents, such as Claude Code and Codex, on one project at once.

You talk to one coordinator agent. It gives each task to a subagent in its own Git worktree, checks the result itself, and merges or pushes it under your project's rules. Every agent stays in a terminal tab you can open and type into.

For developers who already use a command-line coding agent and want several working on one repository for hours, on one Linux machine, without losing track of them.

Get started How it works Source
  • Core tools: Linux only, Python 3.10+, nothing to build
  • Needs Herdr, a separate terminal server
  • Pre-1.0; the session tool, agentctl, is beta

Why

Why it exists

One coding agent in one terminal is easy to watch. Several long-lived agents on one machine, supervised by one person who is not always at the keyboard, run into a different set of problems.

Agents trip over each other

Two agents in one checkout overwrite each other's edits and branches, and one runaway build can fill the disk for everyone.

wrkslots gives every agent its own Git worktree slot on its own branch, with per-slot resource limits and, optionally, its own sparse disk image.

Prompts get lost or sent twice

A follow-up typed into the wrong terminal, or resent because the first attempt looked like it failed, is easy to miss and hard to undo.

agentctl delivers through a durable queue, checks the recipient before and after every keystroke, and sets aside a delivery it cannot confirm instead of replaying it.

Background agents are hard to trust

An agent you cannot watch or interrupt is an agent you have to take on faith.

Every agent runs as its own terminal interface in a tab of Herdr, a persistent terminal server, so you can attach to any of them and type.

Cleanup destroys work

Deleting a worktree that a process still uses, or one that holds unpushed commits, throws away work.

wrkslots deletes a slot only when the evidence shows nothing still uses it: its time-to-live has run out and its owner is dead, or the owner handed it back with a handoff note. Independent process, Git and path checks must agree, unpushed commits are saved first, and if a check cannot be made, it refuses.

"Done" is only a claim

A subagent that reports "tests pass" has said something. It has not shown it.

The coordinator follows the coordinator skill, a Markdown file of instructions it reads at start-up. It reads the diff, the test output and the pushed commit itself before calling work done, lands it under the project's own rules, and tells you what it did not check.

The supervisor is away

Work carries on while you are in a meeting or on your phone, and questions pile up.

agentctl chat connects a chat space to the coordinator. Google Chat works today: the bridge polls the space, once an hour by default, and setup asks whether to shorten that. The optional vibe-talk service is a phone reader and voice for a chat space. It never talks to the coordinator itself, and using it with agentctl chat today needs a piece you supply: a Discord-compatible bridge so vibe-talk can read Google Chat, or an agentctl chat adapter for Discord or Slack.

A sandbox blocks the last step

An agent confined from the network can do all the work and still be unable to push it.

herdr-run runs an allowlisted command, such as git push, in a visible Herdr pane outside the sandbox and records every run. The allowlist is yours to set.

Shared limits run out quietly

Several agents share one machine's CPUs and memory, and often one GitHub account.

dagrun runs validation as a graph under CPU and memory limits. gh-paced paces gh calls, and agent-usage reads plan usage without a model call.

Architecture

How it fits together

A project that adopts the suite becomes a harness: a directory that holds the project's primary checkout, a folder of agent slots, a copy of agent-utils, and an AGENTS.md that makes the agent started there the coordinator. The repository's own documents also call agent CLIs such as Claude Code and Codex "harnesses"; this site calls those agent CLIs and keeps "harness" for the directory.

Read the architecture in depth: each layer's job, a delegated task from start to finish, the harness directory, and where state lives.

Tools

The tools

agentctl and wrkslots are always set up. The chat bridge is core too, but you can connect it later. Setup offers most of the rest; agent-usage, cpuset-alloc and parallel-experiment-runner are used directly. Any of them can be added later by asking the coordinator, and each also works on its own.

Core

agentctl corebeta

Named, durable agent sessions. Start, message, read and stop coding agents by name, with launch profiles you write and prompt delivery that never repeats an uncertain submission.

User guide for agentctl

wrkslots core

One isolated Git worktree slot per agent, with ownership records, handoffs, salvage of unpushed work, and removal only after proof that nothing still uses the slot.

README for wrkslots

agentctl chat coreconnect later

Connects a chat space to the coordinator: your messages are typed into its pane and its marked replies go back to the thread. Google Chat works today; the bridge polls the space, once an hour by default.

Chat guide for agentctl chat

Herdr external

A separately installed, persistent terminal server. Every agent runs as its own terminal interface in a Herdr tab. The suite was last tested with Herdr 0.8.

Optional

herdr-run optional

Runs an allowlisted command, such as git push, in a visible Herdr pane outside whatever confines the agent, and records every run. A cooperative safety rail, not a security boundary.

Quickstart for herdr-run

tick-hub optional

One scheduled tick checks many recurring duties, each on its own cadence. When a tick's output contains an ACTION: line, a small timer script sends that output to the coordinator.

dagrun optional

Runs validation as a dependency graph under CPU, memory and named-resource limits, with cgroup containment. This repository validates itself with it.

wrkviz optional

A zoomable local timeline of what the coordinator and its subagents did, built from their transcripts. Only its summary stage makes model calls.

Adopt it

Adopt it for a project

You do not install the suite by hand. Open your coding agent in the project's Git checkout and give it one sentence. A setup skill does the rest, and asks for your yes before it changes anything.

  1. Tell your agent

    Adopt agent-utils for this project, following skills/agent-utils-setup/SKILL.md from https://github.com/rrnewton/agent-utils.

    That sentence is the whole entry point. Say it to Claude Code, Codex or another agent CLI the setup skill supports, while logged in.

  2. It detects

    The project (remote, default branch, uncommitted changes, worktrees, submodules), the agent CLIs on your PATH, and what the host offers: Git, Python, Herdr, a user systemd manager and cgroup v2, passwordless sudo or fuse2fs for disk-image slots, user namespaces, and optionally cargo, podman and gh. It always shows you this dependency table before it asks anything.

  3. It asks

    About ten questions in small batches, each with a recommended default. They cover the checkout's folder name, whether to track the harness in Git, where agent-utils comes from, launch profiles, the Herdr workspace, the number of slots, slot storage, the file-system sandbox, reclaimable build caches, and whether to connect chat now. Answering "defaults" accepts them all.

    Launch profiles are your policy: it writes exactly what you say and never invents models, flags or permission settings.

  4. It shows the plan, then acts

    It lists every move, file, command and install, and changes nothing on disk until you approve. It installs a missing dependency only with your agreement, prefers user-level installs, and never changes host configuration.

  5. It checks and hands over

    It runs read-only checks of every tool and offers a throwaway round trip: a slot, a worker, a handoff, then removal. Then it starts your coordinator and ends its own session. Without chat, the coordinator is the registered agentctl session coordinator, which timers and scripts can reach; with chat connected, the chat bridge starts it instead.

What you end up with

~/work/foobar/             the harness; the coordinator runs here
  AGENTS.md                makes the agent here the coordinator
  CLAUDE.md -> AGENTS.md
  foobar/                  your checkout, moved in unchanged
  agent-utils/             tools in bin/, skills in skills/
  worktrees/               wrkslots: slots and their registry
  bin/agent-liveness       has a slot's agent stopped?
  .agents/skills/          links to the suite skills
  .claude/skills -> ../.agents/skills
  .agentctl/profiles.json  launch profiles; private
  .wrkslots.yml            slot policy, commented

The harness is its own small, local Git repository, and your primary checkout stays an independent repository inside it. The core tools need no build: they run from the agent-utils checkout on their Python edition. gh-paced and agent-usage are built with cargo, and vibe-talk is deployed separately. Later changes ("connect this to Google Chat", "add dagrun for our tests") are requests to the coordinator, which records each one in AGENTS.md.

The quickstart walks through one recorded run on a one-commit repository, including the deviations it discloses. The setup skill is the procedure itself.

Engineering

How it is built

Each of these is a mechanism you can read in the repository.

Two editions, one contract

Five tools (dagrun with its cpuset-alloc companion, tick-hub, pr-landing-planner, herdr-run and agentctl) are written twice, in Python and in Rust, as independent implementations. Differential tests run both editions on the same representative, adversarial, boundary and seeded-random inputs, and compare machine output, exit behavior and state.

They share core contracts, not every feature. Each edition's extensions are listed, and an audit in October 2026 found the editions differing in places the differential tests do not compare.

What is compared Editions

One validation graph

Every portable check (Python, Rust, cross-language, packaging, browser tests and the vibe-talk service) is one dependency graph, run by the suite's own dagrun under shared CPU, memory and named-resource limits.

make validate runs only what a change can affect and names what it skipped. A path nobody has classified runs everything. make validate-all and a nightly job run the whole graph.

validation.dag.yaml The selector Policy

Fail closed

When evidence is missing, the tools refuse and say why. wrkslots will not remove a slot it cannot prove idle. cpuset-alloc will not fall back to an affinity mask a process can escape. gh-paced charges a command it cannot classify as a write. The source-checkout dispatcher never silently swaps one edition for the other.

wrkslots CPU reservations The dispatcher

How status is reported

Badges use plain words such as core, optional, experimental and beta. A check the host cannot run is reported as skipped and never counted as a pass, and hosted CI declares itself partial for the checks it cannot run. Guards come with self-tests that prove they can fail. This repository's own CI reports to a person; it does not block merges.

The tool is the manual

Each tool's quickstart, embedded user guide and --help are its primary documentation. The agent skills point to them instead of copying them. Seven tools have a public related-work comparison that says what is not new and when an existing project fits better; dagrun, tick-hub, pr-landing-planner and parallel-experiment-runner do not have one yet.

Maturity, plainly

  • Linux only for the harness tools, which rely on a user systemd manager, cgroup v2 and /proc. agent-usage also runs on macOS.
  • Every version is below 1.0, and agentctl calls itself beta.
  • Herdr is a separate project, last tested at 0.8.
  • The chat bridge's working transport is Google Chat. It polls the space, once an hour by default, and setup asks whether to shorten that. The plugin protocol for other providers has no provider yet.
  • The slot sandbox and the herdr-run allowlist guard against accidents by cooperative agents. They are not security boundaries.
  • Packages install from this repository; this site claims no package-index release.
