Tools

The tools

Each tool below starts with the problem it solves, then what you get and what it needs. Status and editions are stated as the repository's own documents state them. A tool's own quickstart, user guide and --help stay the authority for how to use it.

Several tools exist twice, as independent Python and Rust implementations called editions; the badge on each tool says which it has. Paired editions follow a two-edition contract: they share their core commands and output, and each one's extras are listed. A harness runs the Python edition unless you ask for Rust.

Core

agentctl and wrkslots are always set up; the chat bridge is core too, but you can connect it later. Together they let one coordinator delegate safely: named sessions, isolated workspaces, and a way for you to reach the coordinator.

agentctl

corebetaPython + Rust

One interface for starting, messaging, reading and stopping persistent coding agents, while each agent's own terminal stays open to a human.

Problem
A coordinator, or a person, runs several long-lived agents. Follow-up work has to reach the right one exactly once, their output has to be readable, they have to survive crashes, and you still want to type into any of them directly.
What you get
Named sessions in a local registry. A durable prompt queue that tells "safely pending" (exit 75) apart from "possibly submitted" (exit 76) and never replays the second. Launch profiles that you write. Pause, attach and resume for taking over, and revive and adopt for recovering after a crash or restart.
Needs
Linux, Python 3.10 or newer (or a Rust build), and Herdr for interactive control. No hosted account and no always-running manager process.
Use it when
You delegate to agents that persist between prompts, from a coordinator, a script or your own shell.
Status
Core. The agentctl skill calls it beta software, and both editions are at version 0.1. agentctl wait reports readiness for input, not completion, and a successful start or send proves delivery, not that the work is done.
Editions
The Python and Rust editions share the interactive core and one user guide. The Python package adds headless workers, the polling Google Chat transport and launcher, and an MCP interface. The Rust crate adds the event-driven plugin chat host, a coordinator inbox (agentctl inbox), codex-goal and --project-box.

Key capabilities

  • start, send, read, wait, status, list and stop on named sessions.
  • Checks the recipient pane before and after every keystroke, reads it back to confirm delivery, and quarantines a probable misroute.
  • Launch profiles in a private, git-ignored .agentctl/profiles.json: which agent CLI (the profile's harness field), mode, model, effort, literal arguments and environment, passed without shell expansion.
  • start --slot runs an agent inside a wrkslots slot's box.
  • doctor compares the registry with what Herdr reports; capabilities lists what this installation includes.
  • agentctl skill install installs its bundled skill for supported agent CLIs.

wrkslots

corePython

Gives each agent its own Git worktree slot on its own branch, records who owns it, and removes it only after proving nothing still uses it.

Problem
Several agents on one machine need checkouts that do not collide, do not fill the disk, and do not lose work when an agent dies. Cleanup has to be safe even when the original owner is gone.
What you get
Slots for agents (salvaged before removal) and for validation (disposable). Handoffs stored outside the checkout, and release while the owner keeps running. Removal that fails closed. An append-only, hash-linked event history with crash recovery. Audit and unpushed-work reports, and holds for anything a human must keep.
Needs
Python 3.10 or newer, Git and Linux /proc. Disk-image slots need mkfs.ext4 plus passwordless sudo or fuse2fs with /dev/fuse. Running a command in a slot's box needs a systemd user manager and either unprivileged user namespaces or passwordless sudo.
Use it when
More than one agent works on the same repository at once, or you have to clean up after agents you did not start.
Status
Core, at version 0.6. The box is "an accident boundary for cooperative agents", not containment against a hostile one. The FUSE image backend is about ten times slower for metadata-heavy work than the kernel backend.
Editions
Python only, an explicit exception to the two-edition contract. A read-only Rust observer, wrkslotsd, exists for diagnostics.

Key capabilities

  • create provisions and registers a slot on a fresh branch in one step.
  • Reclaim requires an expired time-to-live, a "dead" verdict from the project's liveness command, a dead exact owner process, and agreement from process, mount, Git and path checks. Unavailable evidence refuses.
  • Salvage pushes only to configured remotes; otherwise it writes a verified local Git bundle, and removal refuses if it cannot.
  • Disk-image slots: one sparse ext4 image each, about 70 MiB when fresh.
  • wrkslots run SLOT -- CMD: per-slot systemd limits, a fresh /tmp, and a view in which only the slot and named paths are writable.
  • status --all-machines, doctor, audit, unpushed, hold, clean-caches and recover.

agentctl chat

coreconnect laterPython + Rust, different bridges

Connects a chat space to one coordinator running in Herdr: allowed messages are typed into its pane, and its marked replies go back to the original thread.

Problem
You want to hand the coordinator work, and hear back, while you are away from the terminal, without giving every worker its own chat connection.
What you get
Messages from allowlisted senders only, stored durably before anything else happens. A reaction that means "received", not "done". Replies the agent writes between marker lines in its own output, posted to the right thread and retried under a stable request ID so they are not posted twice. A delivery whose outcome is uncertain is recorded, never retyped.
Needs
Herdr. For Google Chat: a space ID, your user ID for the allowlist, and an OAuth access token or a command that prints one.
Use it when
You want to reach the coordinator from chat. Without it, you talk to the coordinator in its Herdr tab.
Status
Core, and setup lets you connect it later. Google Chat works today through the polling transport, once an hour by default; --interval sets a shorter cycle, down to a fraction of a second, and an operator-supplied event command delivers messages at once. The subscription-plugin protocol has no shipping provider yet. A coordinator started with chat launch belongs to the bridge's shell, not to agentctl's registry, so agentctl send coordinator, which tick-hub's delivery script uses, does not reach it. Prompts arrive as pasted terminal input, not through the agent CLI's own protocol, and reply capture depends on Herdr's bounded scrollback, so a clipped reply fails visibly rather than being guessed.
Editions
Two different bridges. Python: Google Chat polling, operator adapters, chat launch to start a coordinator and its bridge together in one Herdr pane, and chat context. Rust: an event-driven host for an installed subscription plugin, a separate one-shot outbound helper, and sent and thread for checking delivery. The agentctl-chat skill describes the Rust bridge.

Key capabilities

  • One bridge connects one configuration to one coordinator; attachments are not forwarded.
  • Several replies per request are allowed, including progress updates.
  • Restart-safe: requests and replies live in the bridge's state directory.
  • In the Rust protocol, a provider gap stops the bridge rather than risking a silent loss; automatic reconnect after a gap is refused.

Herdr

externaltested with 0.8

A separately maintained, persistent terminal server. Every agent in a harness runs as its own terminal interface in one of its tabs.

Problem
Coding agents need a terminal that outlives whatever started them, and a person needs to be able to attach to any agent's real interface and take over.
What you get
Workspaces, tabs and panes with a command-line and socket interface. agentctl uses it to open tabs, deliver prompts and wait for readiness; the chat bridges and herdr-run also run through it, each with its own adapter.
Needs
Install it from its upstream project, then start it once with herdr. The setup agent offers to install it if it is missing.
Status
External. agent-utils was last tested with Herdr 0.8; if a newer release misbehaves, report the version.

herdr-run

optionalPython + Rust

Runs an allowlisted command in a visible Herdr pane, outside whatever confines the caller, and returns its real output and exit code.

Problem
An agent whose sandbox blocks a legitimate operation, such as git push, gh or a dependency fetch, needs a sanctioned, visible and recorded way to run it. The pane is not a child of the caller, so the caller's network policy, environment and lifetime do not apply to the command.
What you get
A per-project allowlist (.herdr-run.yaml) that only a person widens. Byte-exact standard output and error, the command's own exit status, and distinct codes for refusals and wrapper failures. A private audit log of refusals, admissions and completions, in a pane anyone can watch.
Needs
Linux with a working systemd user manager, and Herdr (tested with 0.8.0).
Use it when
An agent must run a specific, approved command that its own sandbox refuses.
Status
Optional, at version 0.4. Its allowlist is "a cooperative safety rail", not a containment boundary against a hostile process running as the same user. A command that outruns its timeout keeps running. The audit log is best-effort. Its end-to-end differential tests run against a fake Herdr.
Editions
Python and Rust, cross-checked by the differential tests.

Key capabilities

  • Splits the command, checks the bare program name against policy, re-quotes every argument, and refuses known self-escapes.
  • Captures results through files, not by scraping the screen.
  • Will not type over a person: readiness checks are conservative, and one lock per pane serializes use.
  • Bounded tabs: at the cap, a new tab replaces the least recently used idle one, and reap reports finished ones.
  • Run records are pruned after four days by default. net-doctor checks that a pane can reach what the caller's sandbox cannot.

tick-hub

optionalPython + Rust

One cron job, timer or heartbeat evaluates many recurring duties, each on its own cadence, and prints stable lines such as HEALTH:, ACTION:, NOTE:, ERROR: and NO_RESULT:.

Problem
A coordinator has many recurring duties: status reports, freshness checks, conditions a shell command can test. Without tick-hub each needs its own timer, and each speaks its own format.
What you get
Reminders with a cadence, flags, shell gates and dependencies. File-freshness checks reported as ok, stale or missing. A deterministic line protocol, state written only when you pass --flush, and strict JSON or YAML configuration.
Needs
Python 3.10 or newer, or a Rust build. In a harness, the delivery script and timer come from the setup templates and need a user systemd manager.
Use it when
The coordinator should be reminded of something on a schedule, or told when a file has gone stale.
Status
Optional, at version 0.2. It does not schedule itself or deliver what it prints; in a harness, a small tick-deliver script run by a 15-minute timer sends the tick's output to the coordinator with agentctl send whenever it contains an ACTION: line. Action handlers must be idempotent, because an interrupted run can emit an action before its state is written. There is no related-work document yet.
Editions
Python and Rust, cross-checked by the differential tests.

dagrun

optionalPython + Rust

Runs a dependency graph of build and test steps with bounded concurrency, resource-aware planning, Linux cgroup containment and per-step profiling.

Problem
Validation run one step at a time is slow. Run all at once, it overloads a shared machine, and one runaway step can take the host with it.
What you get
Steps run in dependency order under separate limits on active steps and total CPUs. Admission accounts for memory and for scarce named resources such as a browser. Every step is boxed in a cgroup. You also get profiles, speedup sweeps, and timeouts that freeze evidence before they kill.
Needs
Python 3.10 or newer, or a Rust build. Containment needs Linux cgroup v2 and a delegated systemd user scope. Without them a run exits with status 3 unless you pass --allow-cgroup-failure and accept running unboxed, with a visible warning.
Use it when
Your checks could run in parallel but must share one machine politely. This repository runs its own validation graph, more than a hundred steps, through it.
Status
Optional, at version 0.15, the highest version in the suite. Its README says the shared resource-caps file has known gaps that must be resolved before it is treated as a trustworthy host policy. There is no related-work document yet; the planner design surveys the literature.
Editions
Python and Rust, cross-checked by the differential tests.

Key capabilities

  • Strict JSON or YAML graphs with namespaced include fragments; list, ASCII, dot, JSON and YAML views.
  • Planners: greedy longest-first, critical path, and CPA, which picks per-step widths from measured speedup curves.
  • Profiles, parallel-speedup sweeps, and an HTML profile report.
  • dagrun capabilities reports which limits this host can actually enforce.
  • Ships cpuset-alloc and dagrun pin-run for hard CPU reservations.

cpuset-alloc

optionalships with dagrunPython + Rust

Reserves disjoint CPU sets in a durable ledger shared across processes, and hard-pins a benchmark's whole process tree.

Problem
Concurrent benchmarks or jobs on one host need CPU cores that do not overlap, and reservations left behind by crashed processes must be reclaimed safely.
What you get
cpuset-alloc run --cores N --tag T -- CMD launches the command in a cgroup scope verified to be limited to its reserved CPUs, plus status and reclaim. Stale holders are recognized by process ID and start time.
Needs
Linux cgroups. It is a companion command inside the dagrun distribution and crate; setup does not offer it separately.
Status
It refuses to run when hard pinning cannot be proved, and never falls back to an affinity mask a process could escape. status also sweeps stale records, so read the ledger file first when crash evidence matters.

parallel-experiment-runner

optionalPython

Runs concurrent seed-sweep workers under dagrun's containment, each with enforced CPU, memory, process-count and wall-clock limits.

Problem
Chaos searches, fuzz sweeps, flaky-test hunts and parameter scans can pile up processes and saturate a host.
What you get
Each seed becomes one boxed dagrun step. Concurrency is sized from measured idle-core headroom, never more than 316 workers, after a short calibration ramp. A cost estimate comes first (or an explicit UNSET) and measured actuals after. A breach ends in a clean kill of the whole subtree that names what was breached.
Needs
Python 3.10 or newer, dagrun, and Linux cgroup v2. It refuses to run uncontained (exit 3) unless you pass --allow-cgroup-failure.
Status
Optional, at version 0.3, and not offered by setup. In its own words, "a resource box against a BUG in our own code, NOT a security sandbox": no seccomp and no user-namespace isolation. There is no related-work document yet.
Editions
Python only, an explicit exception to the two-edition contract.

wrkviz

optionalPython

Builds a self-contained, zoomable local website from agent transcripts: a timeline of what a coordinator and its subagents did.

Problem
After days of multi-agent work it is hard to see who did what and when, how agents forked and joined, and what each phase achieved.
What you get
One track per agent, with fork and join edges and active, tool, waiting and idle intervals. Cached summaries from phrase level up to quarterly. A static site served on 127.0.0.1 with no CDN, and a command-line query tool. It imports Codex and Claude Code transcripts, including nested subagents.
Needs
Python 3.10 or newer. Summaries use an installed codex CLI by default, or Claude Code, or an offline heuristic backend; ingestion, formatting and serving use only the standard library.
Use it when
You want to look back at a long run, explain it to someone, or keep an archive of it.
Status
Optional, at version 0.1. Only the summarize stage spends model calls, and a failed backend never silently falls back to another model. Hosted serving is deliberately deferred, and one refresh writes one team's archive. Archives contain transcript text; treat them like the logs.
Editions
Python only, an explicit exception to the two-edition contract.

gh-paced

optionalbuild from sourceRust

A wrapper in front of the GitHub CLI that charges every gh call against per-host budgets and waits, or refuses, before GitHub has to push back.

Problem
gh does no pacing. Agents looping over it, on several hosts that share one account, can trip GitHub's secondary rate limits, and an account that keeps calling after that risks suspension.
What you get
Each call classified as read, search, write or credential, and charged against budgets sized so four hosts sharing one account stay well under GitHub's documented limits. One write in flight at a time. A 15-minute pause after any rate-limit, abuse or 403 response. A guard that refuses oversized or base64-heavy write bodies, and watch loops refused unless you allow them.
Needs
Linux, the real gh binary, and a Rust toolchain to build it.
Status
Optional, at version 0.1, built from rs/ and in no package index; no agent skill. Budgets are per host, hosts do not share state, and only calls made through it are paced. It classifies from the command line, so it cannot see the HTTP requests gh makes itself. It lowers the risk of tripping limits; it cannot promise an account will never be limited.
Editions
Rust only.

agent-usage

optionalbuild from sourceRust

Reports plan usage, reset times and burn rates for Claude Code and Codex, plus local token use, without making a model call.

Problem
Agents cannot see their own budgets. A person can type /status, but for an agent, starting a throwaway session to read it costs a full start-up, and probing with a model call costs tokens.
What you get
Each plan window the provider reports, with percentage used and reset time. Burn over 15 minutes, 1, 3 and 24 hours, and whether a window would fill before it resets. Local token use from transcripts. Text, JSON, one-line or cached output, and an optional background process that keeps 15-minute history.
Needs
Linux or macOS, curl, optionally sqlite3, and a Rust toolchain to build it.
Status
Optional, at version 0.1, built from source and in no package index. Setup does not offer it and it has no agent skill. Plan percentages exist only for subscription logins; API-key, cloud-provider and gateway setups get local burn only. Its tests run against fakes, and its README lists what it has not measured.
Editions
Rust only.

vibe-talk

optionalearlyRust service

A small Rust web server and phone web app for reading, discussing and replying to your agents' chat messages, with summaries, read-aloud and voice conversation. Its own page shows it in five short clips, recorded against local mocks.

Problem
Agents post long messages, often many before you look. On a phone, and especially by ear, you need a short summary of each, a way to ask for one particular message in full, and a way to reply.
What you get
A phone web app with main, thread and all-message views, drafts, an outbox, reactions and search. Summaries and thread names. Read-aloud through ElevenLabs or the phone's own speech engine, and voice conversation. An MCP endpoint and a JSON API. Separate read and write tokens, configured channels as an allowlist, and posts that cannot ping @everyone, @here or a role; a reply notifies only the users its text mentions.
Needs
A host to run it (a native build or a container), something in front of it that terminates TLS if you expose it (the microphone needs HTTPS), a chat-provider credential, and optionally a voice vendor and a model provider for summaries. It is a bridge, deliberately not run next to the coding agents.
Status
Optional and early, at version 0.0.1. In its own status table, Discord reading and posting are written and unit-tested but have never run against live Discord. The voice-agent path has not been shown working end to end, model summaries have met only a local mock, and device speech is a prototype. Reading through a compatible Google Chat bridge has seen real read-only traffic. Slack support is tested against a local fake.
Editions
One Rust implementation with its own Cargo workspace, lockfile and CI workflow, outside the two-edition contract. A service, not a command-line tool, and it has no agent skill.

pr-landing-planner

experimentalPython + Rust

An advisory planner that turns a queue of pull requests into per-PR actions and conflict-safe groups.

Problem
Landing many pull requests means working out which ones conflict, what order they must go in, whose CI evidence still applies to the exact head, and which can land together.
What you get
Real merge-conflict detection, dependency ordering, CI classification, and evidence that must name each PR's exact head. Output for people, as canonical JSON, or as line-oriented actions. An offline fixture mode, and a live mode that uses gh and git against a local clone.
Needs
Python 3.10 or newer, or a Rust build; gh and git for live mode. Fixture mode needs no network.
Status
Experimental, at version 0.1. It "never merges, rebases, labels, refires, or otherwise mutates a pull request"; live mode only updates private refs in the clone you give it and may write a local plan archive. A separate, authorized operator does any landing, guided by the pr-landing-operations skill, and only where the repository's own rules allow it. There is no related-work document yet.
Editions
Python and Rust, cross-checked by the differential tests.

Agent skills

documentation for agents

Instructions written for agents, designed as one set: two suite skills, and one skill for most tools with a command.

Problem
An agent needs consistent rules for setting the suite up, running a project as coordinator, and using each tool, and a copied manual drifts from the installed tool.
What you get
The setup skill (the adoption procedure, its templates and "add a tool later" recipes) and the coordinator skill (priorities, delegation, supervision, landing, reporting, shared-machine safety). Tool skills point to each tool's quickstart, --help and user guide instead of copying them.
Status
Setup links four skills into a harness by default (setup, coordinator, agentctl, wrkslots) plus those of the optional tools you choose. gh-paced, agent-usage and vibe-talk have no skill. herdr-agent's skill covers the older interface.

chat-subscription libraries

libraryRust

Two Rust libraries that define how chat providers plug into the Rust chat host as separate processes.

Problem
A chat bridge must not lose or double-process messages across disconnects, and providers should plug in as separate executables without a dynamic-library interface or credentials in the protocol.
What you get
chat-subscription: ordered events, opaque replay cursors, explicit checkpoint and gap events, and a durable acknowledgement boundary. chat-subscription-plugin: the same contract as a bounded, versioned, length-prefixed JSON process protocol, with a Linux process host and a deterministic fake provider for conformance tests.
Status
Version 0.1 libraries with no commands. No provider plugin ships yet. Plugins are trusted same-user code; the private process group is for cleanup and supervision, not containment.

Installing a tool on its own

In a harness the core tools need no installing: the commands in agent-utils/bin run straight from the checkout on the Python edition. The exceptions are gh-paced and agent-usage, which are built with cargo, and vibe-talk, which is deployed separately. To use one tool outside a harness, install it from a checkout of this repository:

python3 -m pip install ./py/wrkslots      # a Python distribution
cargo install --path rs/agentctl          # a Rust crate

Every paired tool and every Python-only tool has its own installable distribution; gh-paced and agent-usage are built from rs/. This site does not claim that any of them is published to a package index. See the Python distributions and Rust crates for the full lists.
