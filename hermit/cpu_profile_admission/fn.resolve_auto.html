Expand description

The named profile --cpu-profile auto resolves to for a guest program at host path program, with why (detcore::exec_record::auto_profile): from the declarations of the image it execs first and of that image’s program interpreter, where to_host gives the host path of a path as the guest names it, or None where a mount with no source hides it in the launch view: a hidden interpreter refuses, rather than reading the host file its mount target shadows. program is the program in the launch’s completed view (its mounts, binds and image rootfs already applied by the caller), and every script hop is mapped through to_host the same way. A script’s interpreter is followed as the kernel follows it (Detcore’s script_interpreter, the load_script rules: the line and the path end where the kernel ends them, at a newline and at a space, tab or NUL), through a bounded chain of scripts to the image the kernel would exec. Evidence is read strictly: a declaration beside a scan state that could not be decided refuses, rather than selecting from a lower bound. This chooses the profile before launch; Detcore’s check of each executed image and interpreter (Detcore::isa_refusal) is still what refuses a run whose actual objects need more, so a pathname read here can never admit one.

On a host that is not x86-64 no CPU profile is presented: an ELF64 image built for the host’s own machine declares no x86-64 ISA level, so auto names the default profile, which there serves nothing (isa_needs_on). Every other read and refusal is the same as on an x86-64 host.
