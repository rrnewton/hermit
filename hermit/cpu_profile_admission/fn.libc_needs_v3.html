Whether the C library of the image program execs first declares that it needs x86-64-v3, where its own and its interpreter’s declarations do not need to say so (resolve_auto). This is the libc.so.6 in the directory of that image’s glibc program interpreter, after the symlinks of the interpreter’s own name, and then after the symlinks of its own.

glibc’s loader and its C library come from one build (they share GLIBC_PRIVATE), so that file declares what the C library the loader maps declares, and auto does not repeat the loader’s search. CentOS 10’s glibc declares x86-64-v3 in libc.so.6 alone; its loader declares no need.

Paths are read in the launch’s view, as resolve_auto reads them: program is a host path, a script’s interpreter and an absolute symlink target are guest paths mapped through to_host, and a relative target stays in its link’s directory ([followed_in_view]). The C library is opened without blocking and without following a final link, and only a regular file is read, so a FIFO or a device there never makes auto wait. Nothing here refuses. A library that is absent, hidden, unreadable, not a regular file, unmarked, malformed, or declaring another level gives false, and glibc’s own check still refuses a guest that needs more than its profile presents.
