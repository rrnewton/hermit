Known-gap ledgers. A ledger lists the tests a validation node runs and expects to fail, each with its tracking issue, so that a node can run a whole suite on a backend that does not pass all of it yet without counting a failure as a pass or hiding it.

The format and its readers:

  • ci/kvm-gap-ledger.rs. It is the node’s runner, the static check, and the history gate that make lint-checks runs (lint-check-known-gap-ledgers).
  • The validation DAG generator. It writes each Declaration into its node’s environment as LEDGER_ENV, so ci/dag/validate.json names the file the node judges.
  • ci/compat-envelope/scorecard.rs. It lists every row in SCORECARD.md and in ci/compat-envelope/known-gaps.json, outside every E2E count.
  • The dev-hermit receipt qualifier, owned outside this repository. It reads a node’s LEDGER_ENV declaration from validate.json and the file as committed on main. A diagnostic_fail row qualifies only if its structured-result id equals a row’s Row::id. Do not change HEADER without telling that reader: the header is the schema’s version.

§Format

UTF-8 with LF line endings and a final newline. A line whose first character is # is a comment, wherever it is; a blank line is an error. The first other line is HEADER. Every later line is a row of six TAB-separated fields, none empty and none padded:

ColumnContent
idThe test’s structured-result id, <cargo package>::<test binary>$<test function>, exactly as the node’s results name it. Rows are sorted by it, byte order, with no duplicate.
gapThe reason: a short gap code, no whitespace. The ledger’s comments define each code.
issueThe tracking issue or pull request, as a full GitHub URL.
outcomeHow the failing attempt must end: failed, or cpu_timeout (stopped by its CPU budget).
signatureFor failed, text the test’s output must show (signature_matches) when the node runs it with RUST_BACKTRACE=0, so a panic prints std’s note: run with line rather than a backtrace; it may hold spaces, not TABs, and writes a newline as \n, a backslash as \\ and any run of digits as <N>. For cpu_timeout, -.
approvalbaseline for a row present, unchanged, since the ledger’s introduction; otherwise the full URL of a specific approving comment, review or commit.

§What may change, checked against history

A row excuses one test failing one way: its id, outcome and signature (Row::scope). The history gate (judge_history) holds the ledger to the following rules along the first-parent history that starts at its introduction:

  • A row is a baseline row only if its scope has been in every committed version since that introduction. A row added later, or whose outcome or signature changed, needs an approval URL that a commit-message line binds to its id: KVM-Gap-Approval: <URL> <id>, in the commit that added it or a later one. So the baseline can only shrink, and a swap is an addition.
  • A test that leaves the required set needs approval too. Moving into the ledger is an addition. Leaving the suite, or being #[ignore]d, needs KVM-Required-Removal: <URL> <id>. A rename leaves under the old id.

The required set comes from the suite’s source (suite_tests), whose parser refuses every attribute form it does not understand on the lines it reads. The node also compares that set with Nextest’s list of the built suite, test by test. Together, the parser and the node see every test added, removed or ignored. The history check alone, which is all the portable lanes run, does not: its parser skips an attribute that follows a block comment on the same line, takes a declaration faked inside a string or a block comment for a real one, and does not follow include!, a #[path] or #[macro_use] module, or a macro. Only the node, which runs on KVM hosts, catches a test added, removed or ignored through those.

The walk follows first parents, so the verdict is the same on any linear (rebased) history: on main, which lands by rebase, and on a rebased branch. On a merge commit, a row or removal enters at the merge, and an approval line on the merged side branch is not read: such a change is refused until a commit on the first-parent chain carries the line. GitHub’s checkout of an external pull request is such a merge (refs/pull/N/merge), so a pull request that adds an approved row goes red there until it is rebased.

The walk reads every committed version since the introduction. A version it cannot read (a malformed ledger, a suite form the parser refuses, the suite file renamed) stops it at exit 2, and only a change to the checker can repair that, so a change to a ledger or its suite runs make lint-check-known-gap-ledgers before it lands. Validation runs that target in check.lint_checks (make lint-checks, profiles full, portable and hosted-portable). Renaming the suite file is moving the ledger: a new introduction, reviewed as one.

What no offline check can see stays with review:

  • whether an approval URL really points at the coordinator’s approval of those rows;
  • a test that returns early on one backend;
  • a change to the checker itself;
  • a new ledger, or a moved one, whose introduction starts a new baseline.
