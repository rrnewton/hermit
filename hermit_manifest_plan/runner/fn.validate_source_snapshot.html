pub fn validate_source_snapshot(root: &Path, sha: &str) -> Result<(), String>
Expand description

A --source-sha names the commit of a Git-less snapshot at root, which is then recorded as clean. A directory holding files Git tracks is refused: Git reports their commit and whether they are dirty, and the name would override both. A root with no .git at or above it (an RE worker’s input tree, whether or not git is installed there) is accepted, and so is a snapshot extracted inside a checkout but not tracked by it (ci/buck-e2e/staged/src). Git, not that lexical .git walk, is the authority on being inside a checkout: the walk can find an enclosing .git across a filesystem boundary Git’s discovery will not cross (an EdenFS staged snapshot under a checkout), where Git exits 128 saying it stopped at that boundary. That one answer is not accepted as not-in-Git — a damaged or concealed .git can produce a not-a-repository answer too — it earns one retry with discovery across filesystems and any inherited ceiling removed, and the retry is judged by the same rule as the first answer (tracked refused, untracked accepted, any other failure refused). Every other failure to answer (a plain not-a-repository from a damaged, dangling, or ceiling-hidden .git, a corrupt index, no git to run) is refused: the files might be tracked. The search for .git starts from the resolved root, so a symlink to tracked files is looked up where the files are.

The SHA cannot stand in for this check: it is the claim being checked, and nothing in it says whether an enclosing checkout tracks the root. SNAPSHOT_GIT_ENV may name the git to ask.
