The CPU profile the ptrace verify run of a parity-compared test names ([names_parity_golden_profile]), right after run.

The ptrace verify log is the parity golden (crate::parity::PARITY_REFERENCE_BACKEND), and no candidate backend can carry x86-64-v3: with no profile named, auto presents x86-64-v3 on a qualifying ptrace host and x86-64-v2 on every other backend. The two profiles answer CPUID differently, so the guest’s C library takes other paths and selects other routines, and Detcore’s records (each CPUID check-in, every retired-branch count) differ from the first instructions: the post-pass would compare two different guests. Naming x86-64-v2 on the golden alone gives both sides the same profile. A candidate’s auto already resolves to x86-64-v2 and its record keeps auto’s reason, and a test planned with no candidate keeps auto, so the e2e cells still run auto’s x86-64-v3 where nothing compares it across backends. Which tests are named follows the plan alone (crate::parity::planned_comparisons), never the post-pass’s own switches, which change only what is reported.
