Module backend_order 

Source
Expand description

The backend order of the cell matrix, checked over the union of every run type’s required cells (required_cells): full validation’s (ci/expected-e2e-plan.json) and those of the focused run types, such as super, sabre-compat-only and the archived backends’ archived-nightly, for every execution owner (ci/execution-owners.json).

Two written rules order the backends. Each gives a backend one prerequisite backend (prerequisite):

  • ptrace first (tests/e2e/manifests/README.md, “Matrix symmetry and the test front door”): any active mode must include ptrace, so the reference behavior is established before another backend ratchets it. A dbt, kvm or in-guest-trap cell needs the same test and mode on ptrace.
  • The Subset rule (docs/ARCHITECTURE.md): a result may be enabled or credited for a patcher backend only if the same test and mode pass on in-guest-trap. A liteinst or sabre cell needs the same test and mode on in-guest-trap.

Selecting a cell is the ratchet: the run type that selects it then requires it to pass. So a selected cell whose prerequisite cell no run type selects is a violation, unless EXCEPTIONS_PATH names it with the reason it stays selected. That file is an exact list, like ci/matrix-symmetry-baseline.json: a violation it does not name and an exception that names no violation both fail the check, and every failure names the cell and the missing prerequisite. The check only reads the selection; it never selects or deselects a cell. A longer chain (liteinst, in-guest-trap, ptrace) is checked one link at a time, so each missing link is reported once, on the cell that needs it.

test-harness validate (the gate.manifest validation node) and test-harness sync-cells run check_checkout. test-harness audit-ci runs it too, but no validation DAG node runs audit-ci.

Functions§

check
violations against exceptions: Ok with the excepted violations when the exceptions name exactly the violations; otherwise Err naming every violation no exception names and every exception that names no violation.
check_checkout
check over required_cells of manifests, against the exceptions committed at EXCEPTIONS_PATH under root. Ok with the excepted violations.
parse_exceptions
The exceptions of EXCEPTIONS_PATH’s text. Refuses another schema, an unknown field, an empty about or reason, a prerequisite the order does not give the backend, and a repeated cell.
prerequisite
The backend whose cell, for the same test and mode, a cell on backend needs selected, and the rule that requires it; None for ptrace, the reference. A backend the order does not place is an error, so a new backend takes its place here before any of its cells can be selected.
required_cells
The population the order is checked over: the required cells of every run type (all_run_types), for every execution owner. A cell counts as selected when any run type requires it, so a ptrace cell that only the super run type runs still counts, and a SaBRe cell, which only the archived-nightly and sabre-compat-only run types run, is checked. Occasional tests stay out, as they do from every run type’s selection; only probes beyond the plans, such as the nightly pressure sweep, add them.
summary
The one-line summary test-harness prints after check_checkout passes, naming every excepted cell.
violations
Every cell of cells whose prerequisite cell is not among them, in (test, mode, backend) order. A naked cell has no backend and no place in the order.
