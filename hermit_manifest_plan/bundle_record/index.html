Module bundle_record 

Source
Expand description

What a Buck e2e cell may take from its bundle instead of computing it again.

A Buck validation runs every e2e cell as its own test-harness run process over one immutable bundle (ci/buck-e2e/defs.bzl): the same Hermit binary, harness binaries and source snapshot for each of the 2,248 cells of ci/expected-e2e-plan.json. Two of the harness’s per-cell costs depend on the bundle alone:

  • the SHA-256 of the Hermit binary, taken before and after each cell (about 0.04 CPU-s each for a 62 MB release Hermit);
  • the canonical manifest planner’s acceptance of the source snapshot, a child process of about 0.09 CPU-s whose output the harness discards.

The bundle rule computes both once into BUNDLE_RECORD.json (ci/buck-e2e/bundle-record), and cell.sh names that file in BUNDLE_RECORD_ENV. A cell still checks everything it checked before:

  • The Hermit binary must have the digest the record names, or the cell is an infrastructure error. The digest comes from binary_digest, which hashes a file once per process and again only when its identity changes (device, inode, size, modification and status-change times), and which may also take it from a per-host cache keyed by that identity (DIGEST_CACHE_DIR_ENV). Any write to or replacement of the binary changes its status-change time or inode, so a swapped binary is hashed afresh and refused, and a binary that changes during a cell still makes that cell an infrastructure error.
  • The planner’s verdict is taken from the record only when the record says it accepted this very source SHA with this very planner binary (by digest); in every other case the harness runs the planner itself, as before.
