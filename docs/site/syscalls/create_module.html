create_module (174)

Strategy: determinized-refused · dispatch: pred:is_unimplemented_enosys_syscall · linux determinism: deterministic · target policy: refuse · status: todo · discussion (new)

Summary

create_module(name, size) is the pre-2.6 call that reserved kernel memory for a loadable module. Current x86_64 kernels return ENOSYS; init_module and finit_module replaced it. Detcore returns that same fixed ENOSYS itself and never forwards the call (detcore/src/lib.rs:2090-2094).

Manual reference: Linux man-pages create_module(2).

Linux semantics

Before Linux 2.6, create_module allocated size bytes of kernel memory for a module called name, required CAP_SYS_MODULE, and failed with EEXIST for a name already in use. The module loader was rewritten in 2.6 and the call was dropped. Number 174 now reaches sys_ni_syscall (__SYSCALL(174, sys_ni_syscall) in the generated syscalls_64.h of both kernel trees under /usr/src/kernels on the evidence host), which returns -ENOSYS without reading its arguments and without a capability check.

Flags and options

  • F1: name is NULL or points to unmapped memory: ENOSYS, not EFAULT.
  • F2: valid name with any size, from a caller that looks privileged (Hermit's virtual uid 0) or not: ENOSYS, not EPERM or EEXIST; no kernel memory is reserved.

Determinism analysis

linux_determinism: deterministic. The syscall has been unimplemented since Linux 2.6 and returns ENOSYS on x86_64 without consulting any argument or state.

Nondeterminism sources

  • None on supported kernels; the ABI is an unconditional refusal.

Hermit design

Target policy: refuse. The rendered body carried passthrough from the legacy PASS-THRU recommendation, which predates the code. At hermit f4055eb9cae4 Detcore never forwards create_module to the host:

  • create_module is listed in the Determinized arm of classify_syscall (detcore/src/syscall_classification.rs:275-287; the arm ends => SyscallClassification::Determinized at detcore/src/syscall_classification.rs:688) and in the predicate is_unimplemented_enosys_syscall (detcore/src/syscall_classification.rs:856).
  • The dispatch arm at detcore/src/lib.rs:2090-2094 returns Err(Error::Errno(Errno::ENOSYS)) for every call. It reads no argument and consults no configuration, so the answer is the same with or without panic_on_unsupported_syscalls and under the fail-closed policy.
  • The predicate is part of the refusal boundary is_deterministically_refused_syscall (detcore/src/syscall_classification.rs:1319-1321), which is why code_facts.refused is true.
  • The unit test unimplemented_enosys_syscalls_are_determinized_and_consistent (detcore/src/syscall_classification.rs:2209) pins the classification and the exact predicate set. It does not start Hermit, so it is not ptrace coverage.

Why refuse and not the alternatives:

  • A fixed ENOSYS is exactly what every supported x86_64 kernel returns for this number, so a guest sees no difference from native execution. The doc comment at detcore/src/syscall_classification.rs:851-855 states the same intent: deterministic by construction, without depending on the host kernel being modern.
  • passthrough contradicts the code and would bring back a host-kernel dependence: a pre-2.6 host would expose the host's module table and capability state, and a privileged run would mutate kernel memory.
  • model or emulate would mean reimplementing an interface that current Linux does not provide, which no program running on a modern kernel can rely on.

The code already realizes refuse. What is missing is a test that starts Hermit on ptrace and calls create_module (none names it at this SHA). The classification, predicate and dispatch arm all still carry TODO-HUMAN-REVIEW(#715) (detcore/src/syscall_classification.rs:271, detcore/src/syscall_classification.rs:850, detcore/src/lib.rs:2084; https://github.com/rrnewton/hermit/issues/715). That review concerns the arm as written and does not argue for a different policy.

Recommended tests

  • T1 (covers F1, F2): under hermit run --verify on ptrace, call syscall(SYS_create_module, ...) with (NULL, 0), with ((char *)1, 4096), and with ("hermit_test", 4096). Every call must return -1 with errno == ENOSYS, never EPERM, even though the guest sees uid 0. Shape: a C program tests/c/create_module_enosys.c modelled on tests/c/futex_wake_enosys.c, which calls a raw syscall() and fails unless it gets -1/ENOSYS, with a cell modelled on c-programs/futex-wake-enosys (tests/e2e/manifests/c-programs.yaml:1660, verify with ci: ptrace: true). Neither the program nor the cell exists for create_module at this SHA.
  • T2 (covers none): record and replay a guest that calls create_module once; both the recording and the replay must see -1/ENOSYS, and the replay must not diverge.

2026-07-24 host strace evidence

Test host: Linux 6.17.13 x86_64; strace 6.12.

Ran a syscall-specific safe raw probe with deliberately inert/invalid arguments so privileged or mutating operations could not change host state:

strace -f -qq -e trace=create_module -s 160 python3 -c 'import ctypes; c=ctypes.CDLL(None,use_errno=True); c.syscall(174, *([ctypes.c_long(-1)]*6))'

Actual strace output:

create_module(0xffffffffffffffff, 0xffffffffffffffff) = -1 ENOSYS (Function not implemented)

The trace confirms the host kernel path and observed errno/result for this ABI. The determinism recommendation also accounts for documented success-path state dependencies; an invalid-argument result alone is not treated as proof of determinism.
