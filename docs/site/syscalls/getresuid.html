getresuid (118)

Strategy: determinized · dispatch: typed · linux determinism: conditional · target policy: model · status: todo · discussion (new)

Summary

Returns real, effective, and saved user IDs for the calling process.

Rank 98 in the batch-2 classification sequence after excluding the 50 workload-observed batch-1 syscalls.

Manual reference: Linux man-pages getresuid(2).

Hermit emulates it: Detcore never forwards the call and writes the constant 0 to each result pointer (detcore/src/syscalls/misc.rs:679-694), as part of the fixed virtual-root identity. The target is a per-process credential record that the setters update (owner decision 4).

Linux semantics

The credential subsystem reads current task credentials and maps kernel UIDs through the active user namespace.

getresuid(ruid, euid, suid) writes the caller's real, effective and saved user IDs to three uid_t pointers, in that order, and returns 0. Each ID is converted into the caller's user namespace; an ID with no mapping there is reported as the overflow uid (65534 by default, /proc/sys/kernel/overflowuid). The kernel copies the values out one at a time, so a bad pointer fails with EFAULT after any earlier values have already been written. A NULL pointer is a bad pointer. The host probe under Additional information shows EFAULT for three pointers of -1.

The values change only through the credential-setting calls (setuid, setreuid, setresuid and so on) and through execve of a set-user-ID program.

Flags and options

  • F1: three valid pointers: the real, effective and saved user IDs are written in that order and the call returns 0.
  • F2: a NULL or otherwise invalid pointer in any position: EFAULT; outputs before the bad one have already been written.
  • F3: the reported IDs follow the caller's credential history: setuid-family calls and set-user-ID execve change them, and IDs unmapped in the caller's user namespace read as the overflow uid.
  • F4: every execve copies the effective uid into the saved set-user-ID (after any set-user-ID change), so the saved uid read after an execve equals the effective uid.

Determinism analysis

The triplet is fixed by deterministic credential history under the same container credential assumptions as getuid and geteuid (which the legacy text called pass-throughs; at this SHA they are emulated too, see Hermit design).

linux_determinism: conditional, kept from the legacy classification. On Linux the result is a pure function of the caller's credential history and of the user namespace it runs in; it repeats when the program is launched by the same user with the same namespace mapping, and differs across launching users or mappings.

Nondeterminism sources

  • External credential mutation through unsupported mechanisms
  • User-namespace ID mappings
  • The identity of the launching user, which is the starting point of the credential history

Hermit design

Target policy: model (owner decision 4, 2026-10-04). Detcore keeps a per-process credential record: real, effective, saved and filesystem uid and gid, the supplementary group list and the capability sets. getresuid writes the record's real, effective and saved uids. The record starts with every id 0, fork and clone copy it, and execve keeps it. setuid, setreuid, setresuid update it and apply Linux's own permission rules against the record (CAP_SETUID from the record's capability sets, which a full uid drop clears); their tracking bodies describe the update side. The record is not enforced: the kernel goes on checking the guest's real credentials, root in its user namespace. The legacy recommendation was PASS-THRU; it was superseded by the change tracked in the TODO-HUMAN-REVIEW(#1549) comments, which emulates the whole credential-query family (detcore/src/syscall_classification.rs:657-674). Those comments record why: pass-through returned 0 under the ptrace backend only because the guest runs in a user namespace that maps the launching uid to 0, while in-process backends had no such namespace and leaked the host uid.

What the code does at hermit f4055eb9cae4, where no record exists yet:

  • The dispatch arm calls handle_getresuid (detcore/src/lib.rs:2764); the comment above the arm states the call is "Never forwarded to the host" (detcore/src/lib.rs:2752-2759).
  • handle_getresuid writes 0 to each of the three pointers that is present and returns 0 (detcore/src/syscalls/misc.rs:684-693). The model replaces the three constants with the record's values and keeps the "never forwarded" property.
  • The credential setters setuid, setreuid, setresuid and setfsuid (and their gid twins) are deterministic no-op successes (detcore/src/syscall_classification.rs:961-987, applied at detcore/src/lib.rs:2272-2276), so nothing updates the identity today and F3 always reads 0.
  • classify_syscall returns Determinized for the query family, asserted by the unit test block at detcore/src/syscall_classification.rs:2308-2326.
  • Reduced fidelity (owner decision 3): under --no-namespace (--core-only) or a backend without a user namespace, getresuid still writes the Detcore values while the kernel checks permissions with the launching host user's credentials, so the triplet does not describe what the kernel allows there. No fidelity is required there.

Why model and not the alternatives: emulate, the constant 0 of today, makes a privilege drop invisible, so a program that checks its saved uid after dropping sees the drop fail; passthrough is the backend-dependent leak that the https://github.com/rrnewton/hermit/pull/1549 change removed; refuse would break every program that checks its saved uid before dropping privileges. The accepted cost of model is that the modelled ids are not enforced by the kernel.

Known divergences from Linux:

  • NULL pointer. The handler skips an output whose accessor is None (detcore/src/syscalls/misc.rs:684-692) and still returns 0. The typed Reverie accessor decodes a NULL address as None, so Hermit appears to return 0 where Linux returns EFAULT. T2 should confirm this before a defect is filed.
  • Target (owner decision 6, 2026-10-04): a NULL output pointer gives EFAULT, as on Linux, because the emulated call owes Linux's checks in kernel order. getresuid in kernel/sys.c writes the ruid, then the euid, then the suid with put_user and stops at the first fault, so a NULL euid returns EFAULT with the ruid already written and the suid untouched. The code change is to treat a None accessor at detcore/src/syscalls/misc.rs:684-692 as EFAULT instead of skipping it.
  • Invalid non-NULL pointer. The memory write's error is returned through ? (detcore/src/syscalls/misc.rs:685); the expected guest-visible errno is EFAULT, and earlier outputs stay written, as on Linux. Untested.
  • Credential changes (F3), today. After a successful setresuid(1000, 1000, 1000), Linux reports 1000; Hermit reports 0. The model removes this difference.
  • `execve` (F4). Decision 4 says execve keeps the record, so the saved uid read after an execve is the one from before it. Linux copies the effective uid into the saved set-user-ID on every execve and honours the set-user-ID bit (a documented difference).
  • Thread scope (target). The record is per process; on Linux a raw setresuid syscall changes only the calling thread.
  • `/proc/<pid>/status` is not covered. Its Uid: line shows the kernel's credentials, so it disagrees with the record after a change. That stays an open item for /proc virtualization.

Recommended tests

  • T1 (covers F1): call getresuid with three valid pointers prefilled with -1 and check all three read 0, the record's starting value; run under hermit run --verify on ptrace and under record and replay. Existing partial coverage: deterministic_passthrough_syscalls_verify (hermit-cli/tests/syscall_quick_wins.rs:30) runs tests/c/syscall_quick_wins.c, which calls getresuid with -1-prefilled outputs (tests/c/syscall_quick_wins.c:30-43), checks only that each output changed, and prints the values in its success line (tests/c/syscall_quick_wins.c:145-153) for --verify to compare; the test also checks the strict trace names the call (hermit-cli/tests/syscall_quick_wins.rs:67-81). Its manifest cell is c-programs/syscall-quick-wins (tests/e2e/manifests/c-programs.yaml:9345, verify ci at tests/e2e/manifests/c-programs.yaml:9362-9367). Neither asserts the value 0.
  • T2 (covers F2): a matrix with each of the three pointers in turn set to NULL and to a PROT_NONE page, checking the errno and which earlier outputs were written; compare against Linux natively. A NULL pointer must give EFAULT with the earlier outputs written (owner decision 6); today Hermit is expected to return 0, so this part fails until the handler changes.
  • T3 (covers F3): read-back through the record under --strict on ptrace. As root, setresuid(1000, 1001, 1002) returns 0 and getresuid reports 1000, 1001, 1002. setresuid(-1, 1002, -1) (unprivileged, allowed because 1002 is the saved uid) makes it report 1000, 1002, 1002; setresuid(0, -1, -1) then fails with EPERM and the triplet is unchanged. A forked child reports the same triplet.
  • T4 (covers F4): after setresuid(1000, 1001, 1002), execve an ordinary helper that prints getresuid. Linux reports 1000, 1001, 1001. Assert 1000, 1001, 1002, because decision 4 keeps the record across execve (a documented difference), identically across runs.
