setuid (105)

Strategy: determinized · dispatch: pred:is_credential_identity_noop_syscall · linux determinism: conditional · target policy: model · status: todo · discussion (new)

Summary

setuid(uid) changes the calling thread's user IDs. A privileged caller sets all of them; an unprivileged caller can only switch its effective uid to its real or saved uid. Hermit never forwards the call. Today it returns 0 for every argument and changes nothing, so the guest always presents as the fixed virtual root (getuid and friends return 0). The target (owner decision 4) is a per-process credential record in Detcore that setuid updates under Linux's permission rules and the getters read back, without kernel enforcement. See setuid(2).

Linux semantics

The kernel (__sys_setuid) maps uid into the caller's user namespace and then branches on privilege:

  • If the caller has CAP_SETUID in that namespace, it sets the real, effective, saved and filesystem uids.
  • Otherwise it may only set the effective and filesystem uids, and only to the current real or saved uid.

The new credentials are installed with commit_creds, which also does two things:

  • applies the capability rules for a transition away from or to uid 0;
  • resets the dumpable flag when the effective or filesystem uid changes.

The syscall acts on the calling thread only. POSIX requires the change for the whole process, so glibc's setuid() wrapper repeats it on every thread through an internal signal. The call returns 0 or a negative errno and reports no other value; the result is seen later through the credential getters, through file ownership and through permission checks.

Flags and options

  • F1: caller has CAP_SETUID in its user namespace: real, effective, saved and filesystem uid all become uid
  • F2: caller lacks CAP_SETUID and uid equals its real or saved uid: only the effective and filesystem uids change
  • F3: caller lacks CAP_SETUID and uid is any other value: EPERM
  • F4: uid has no mapping in the caller's user namespace, including (uid_t)-1: EINVAL
  • F5: identity call, setuid(getuid()): succeeds and leaves every uid as it was
  • F6: capabilities: when the effective uid changes from 0 to nonzero, the effective capability set is cleared. When the real, effective and saved uids all become nonzero, the permitted set is cleared too. PR_SET_KEEPCAPS and SECBIT_NO_SETUID_FIXUP suppress these rules. A change from nonzero to an effective uid of 0 restores effective capabilities from the permitted set.
  • F7: dumpable: when the effective or filesystem uid changes, the process's dumpable flag is reset to the fs.suid_dumpable sysctl This changes who owns /proc/<pid> files and who may ptrace the process.
  • F8: thread scope: the raw syscall changes only the calling thread. glibc's setuid() applies it to every thread through its internal set-id signal, so the two entry points differ in a multithreaded process.
  • F9: observers: after a change, getuid/geteuid/getresuid and the Uid: line of /proc/self/status report the new IDs. New files are owned by the new filesystem uid. Permission checks for open, kill and ptrace use the new IDs.
  • F10: RLIMIT_NPROC: since Linux 3.1, a privileged change to a uid that is already over its process limit still succeeds. The kernel marks the process, and its next execve fails with EAGAIN.

Determinism analysis

linux_determinism: conditional. The result depends only on four inputs:

  • the caller's current credentials and capabilities,
  • the user-namespace mapping,
  • uid,
  • for F10, how many processes the target uid owns.

Nothing in the call races. It repeats when Hermit starts every run with the same identity and mapping, and when no process outside the container that runs as the target uid comes or goes. That last condition matters only for F10.

Nondeterminism sources

  • The real uid, saved uid and capabilities the guest is started with. They are inherited from whoever launched Hermit; the 2026-07-24 probe ran as host uid 212630.
  • The user-namespace mapping, which decides F4.
  • CAP_SETUID, which decides between F1 and F2/F3, and through F6, F7 and F9 which later file operations succeed.
  • The process count of the target uid on the host (F10).

Hermit design

Target policy: model (owner decision 4, 2026-10-04): setuid updates the per-process credential record described under "Target: the credential record" below. The code at hermit f4055eb9cae4 has no such record. Today setuid is an argument-blind no-op:

  • setuid is classified Determinized at detcore/src/syscall_classification.rs:647. The batch-38 rationale for the whole credential-setting family is at detcore/src/syscall_classification.rs:636 (tagged TODO-HUMAN-REVIEW(#787) at line 630).
  • The dispatcher answers it before the typed match, in the arm at detcore/src/lib.rs:2272-2276: SyscallClassification::Determinized if is_credential_identity_noop_syscall(call.number()) => { Ok(0) }. The arm reads no argument, stores nothing and never reaches the host.
  • The predicate is defined at detcore/src/syscall_classification.rs:974, with setuid at detcore/src/syscall_classification.rs:977. It covers the whole setter family: setgid, setresuid, setresgid, setreuid, setregid, setgroups, setfsuid and setfsgid.
  • The getters getuid/geteuid/getgid/getegid return a constant 0 (detcore/src/lib.rs:2760-2763), and getresuid writes 0 to every result pointer (detcore/src/syscalls/misc.rs:679). So the guest always presents as root, whatever it set.
  • The unit test batch38_openat2_and_credential_syscalls_are_determinized (detcore/src/syscall_classification.rs:2265) pins the classification and the predicate membership. It cannot see what the arm returns.

Reconciling the two legacy filings

The legacy filings disagreed on the recommended action:

  • https://github.com/rrnewton/hermit/issues/462 said PASS-THRU. Its reason was that the transition "can remain forwarded under the same fixed container-identity assumptions as getuid".
  • Its duplicate https://github.com/rrnewton/hermit/issues/468 said NEEDS-HANDLER. Its reason was that "a deterministic run must expose virtualized, reproducible credentials".

https://github.com/rrnewton/hermit/issues/468 won, for two reasons:

  • The handler it asked for exists. The code above answers setuid in Detcore and never reaches the host.
  • The premise of https://github.com/rrnewton/hermit/issues/462 no longer holds. getuid is not forwarded any more; it is emulated as 0 (detcore/src/lib.rs:2760). Forwarding setuid next to an emulated getuid would split the guest's view from the kernel's. After a forwarded setuid(1000), the kernel would check permissions as uid 1000 while getuid still reported 0.

Both filings agreed on conditional and on the inputs listed under Nondeterminism sources, and that agreement is kept.

Target: the credential record (owner decision 4)

The owner accepted this target on 2026-10-04. Every credential body (the set*id family, setgroups, capset, the get*id family, getgroups, capget) describes it the same way:

  • Record. Detcore keeps, per guest process, the real, effective, saved and filesystem uid and gid, the supplementary group list and the capability sets.
  • Calls. The set*id calls, setgroups and capset update the record. The get*id calls, getgroups and capget report it.
  • Starting state. Every id is 0, as getuid reports today, and the group list is empty. The capability sets start as the guest holds them at launch in the ptrace container, as uid 0 in a fresh user namespace: permitted and effective full, inheritable empty.
  • Inheritance. fork and clone copy the record; execve keeps it.
  • Permission rules. Each setter applies Linux's own rules against the record, never against host state, so the checks are deterministic. With the matching capability (CAP_SETUID, CAP_SETGID) in the record's effective set, a caller may set any valid id; without it, only the ids Linux allows an unprivileged caller. Linux's capability fixups for uid and filesystem-uid changes apply to the record. So once the guest has dropped to uid 1000 with no CAP_SETUID left, setuid(0) returns EPERM, which is what OpenSSH's permanently_set_uid checks.
  • Valid ids. Every id except (uid_t)-1 and (gid_t)-1 is valid in the record, as in the initial user namespace. Where -1 does not mean "unchanged", Linux rejects it: EINVAL, or for setfsuid/setfsgid no change.
  • No enforcement. The kernel goes on checking the real credentials: the guest stays root in the container's user namespace. After setuid(1000) the guest can still open root-only files, and new files keep the kernel's owner and group. That is the accepted cost.
  • Not covered. The Uid:, Gid:, Groups: and Cap*: lines of /proc/<pid>/status still show the kernel's credentials and disagree with the record; that stays open for /proc virtualization. Effects outside the record (the dumpable flag, the parent-death signal, RLIMIT_NPROC accounting) do not follow a change.
  • Thread scope. Linux credentials are per thread in the kernel, and glibc's set*id and setgroups wrappers broadcast a change to every thread through an internal signal. The record is per process (owner-approved), so a raw syscall on one thread of a multithreaded guest changes the credentials every thread reads back. That is a documented difference. setfsuid, setfsgid and capset have no glibc broadcast, so for them the glibc call differs from Linux too.

What `setuid` must do against the record.

  • With CAP_SETUID in the record's effective set, set the real, effective, saved and filesystem uid to uid (F1, F5). Then apply the capability fixups (F6): leaving effective uid 0 clears the effective set, and when the real, effective and saved uid all become nonzero the permitted set is cleared too, unless the guest has set PR_SET_KEEPCAPS or SECBIT_NO_SETUID_FIXUP (prctl state the model must consult).
  • Without CAP_SETUID, accept uid only if it equals the record's real or saved uid, and then change only the effective and filesystem uid (F2). Any other value returns EPERM and leaves the record unchanged (F3).
  • (uid_t)-1 returns EINVAL for every caller (F4).
  • Afterwards getuid, geteuid and getresuid read the record back (F9).

Differences from Linux

Under the target (documented differences, owner decision 4):

  • No enforcement (F9). After setuid(1000) the kernel still treats the guest as root. Permission checks for open, kill and ptrace and the owner of new files follow the kernel's credentials, and the Uid: line of /proc/self/status disagrees with getresuid.
  • No dumpable effect (F7). The kernel's credentials do not change, so the dumpable flag is not reset.
  • Per-process scope (F8). A raw SYS_setuid on one thread changes what every thread reads back. On Linux only the calling thread changes, and only glibc's wrapper reaches the others.
  • No deferred `RLIMIT_NPROC` failure (F10). The kernel's process accounting never sees the new uid, so the next execve succeeds.

Today, until the record lands (the no-op at detcore/src/lib.rs:2272):

  • No `EINVAL` (F4). setuid((uid_t)-1) returns 0; Linux returns EINVAL for any caller.
  • The drop is invisible (F1, F9). After setuid(1000), getuid() still returns 0.
  • Programs that verify a privilege drop will fail. One example, recalled from upstream source and not checked here: OpenSSH's permanently_set_uid treats a successful setuid(0) back to root as fatal.
  • rr's upstream setuid program, run by rr_setuid at hermit-cli/tests/rr_suite.rs:440, asserts getgid() == new_g after setgid at third-party/rr/src/test/setuid.c:38 and getuid() == new at third-party/rr/src/test/setuid.c:41 (rr pin 39e5c18e7e43 at this hermit SHA). Reading the code, it should fail at line 38 under Hermit. It is #[ignore]d by default and was not run here.
  • No capability effects (F6). capget/capset are passed through (detcore/src/syscall_classification.rs:716, detcore/src/syscall_classification.rs:717). They report the host capability sets, which a no-op setuid never clears.
  • F2 and F3 cannot arise. The guest never stops being the virtual root, so the unprivileged branches are unreachable.

Recommended tests

  • T1 (covers F1, F5, F9): under hermit run --strict --verify on ptrace, in the container:
  • raw syscall(SYS_setuid, 0) and syscall(SYS_setuid, getuid()) return 0, and getresuid still reports 0, 0, 0;
  • then syscall(SYS_setuid, 1000) returns 0; getuid and geteuid return 1000, getresuid reports 1000, 1000, 1000, and setfsuid(-1) returns 1000;
  • the Uid: line of /proc/self/status and the owner of a file created afterwards are recorded, listed as documented differences (they show the kernel's credentials), and identical across runs.

The 2026-07-24 probes used setuid(getuid()) on the host (see Additional information). Existing candidate: rr_setuid (hermit-cli/tests/rr_suite.rs:440), which is #[ignore]d and expected to fail at third-party/rr/src/test/setuid.c:38 until the record lands.

  • T2 (covers F2, F3): setresuid(1000, 2000, 3000) leaves no uid 0, so the record drops every capability. Then setuid(3000) returns 0 and getresuid reports 1000, 3000, 3000; setuid(2000) and setuid(0) return EPERM and leave the record unchanged. Today all of them return 0 and getresuid reports 0, 0, 0.
  • T3 (covers F4): syscall(SYS_setuid, (uid_t)-1) returns EINVAL. Today Hermit returns 0, so this test fails until the model lands.
  • T4 (covers F6, F7): from the starting record, setuid(1000) leaves capget reporting empty effective and permitted sets. In a fresh child, prctl(PR_SET_KEEPCAPS, 1) and then setuid(1000) leave the permitted set full and the effective set empty. prctl(PR_GET_DUMPABLE) is recorded and stays unchanged, a documented difference. Results are identical across runs.
  • T5 (covers F8): in a process with two threads, raw SYS_setuid(1000) from one thread; then getuid returns 1000 in both threads (the per-process record; on Linux the other thread keeps 0, a documented difference). Repeat in a fresh process with glibc setuid(), which gives 1000 in both threads on Linux too. Also assert that glibc's set-id signal broadcast does not change the run's schedule between runs.
  • T6 (covers F10): with RLIMIT_NPROC set to 1, setuid(1000) and then execve both succeed, because the kernel's process accounting never sees the record (documented difference). The result is identical across runs.
