detcore::aarch64_lse

Module elf 

Source
Expand description

Applying the exclusive-loop rewrite to the executable segments of an aarch64 ELF file.

The rewrite is in place and the same length, so the output file is the input file with some instruction words replaced: every offset, segment, symbol, relocation and build id stays as it was, and the loader maps it exactly as it mapped the original.

Only sections marked executable (SHF_EXECINSTR, so .text, .plt, .init and the like) are scanned for rewrites. Bytes an executable segment carries that no such section covers are never rewritten, but their literal and base readers are collected for protection, under their own refusal name (gap-reader-inside-the-sequence): gap bytes are not proved code, so data there (ordinary .rodata in a single R+X load, the GNU ld default) can decode as a reader it is not and refuse sequences only it would refuse. Unaligned gap ends are rounded outward and decoded; only a gap whose bytes run past the end of the file is refused by name. An executable PT_LOAD segment also carries the ELF header, the dynamic symbol and relocation tables and read-only data, and those bytes decode as instructions as readily as code does: measured on one Android test binary, scanning whole segments found 69 “exclusive instructions” of which 66 were in data before .text even began. A file with no section headers is left alone and reported, because nothing in it can be told apart from data.

Within those sections, only code is rewritten (super::mapping). An executable section can hold data too (a literal pool, or OpenSSL’s constant tables in .text), and a table whose words happened to form a canonical loop would otherwise be rewritten, corrupting it. What is taken for code depends on what the file says, section by section:

  • Mapping symbols: exactly the ranges they mark $x. The AArch64 ELF ABI has an assembler mark data $d, so data marked as the ABI says is never taken for code. This is the only evidence the rewrite accepts, because it is the only one that proves where code is. A section that also holds a mapping symbol of another kind (AArch32’s $a or $t, or a $ name this reader does not know, such as $xyz) is not proved by them: its sequences are left alone as unsupported-mapping-symbol, naming the symbol.
  • No mapping symbols: nothing, whatever the unwind table covers. Every exclusive sequence in such a section, as in every stripped file, is left alone as no-mapping-symbols, so the file is left unchanged and named, never silently. An FDE covers its whole function, including a table the function branches over or keeps after a call that does not return, so the unwind table cannot prove which of its bytes are code.

Under any evidence, a sequence an LDR (literal) or ADR in the code reaches is refused (literal-inside-the-sequence): an object linked without mapping symbols after one with them inherits the earlier $x range. The branch analysis still reads every word of every executable section, so a word that might branch into a sequence still refuses it. Gap words contribute decoded direct-branch targets the same way, but they are exempt from the unknown-direct-branch rule section words trip: data in a gap can look like an unallocated branch, and applying that rule to it would refuse nearly every image with R+X data.

A section in a segment that is both writable and executable is refused too: writable text is either a loader quirk or a runtime that rewrites itself, and rewriting it would race whatever writes it.

A sequence any relocation points into is refused as well. Relocations are read as 64-bit little-endian, the only aarch64 ELF this rewriter handles. A relocation is the loader’s licence to change those bytes at load time, which would overwrite part of a rewritten sequence with something computed for the original one.
