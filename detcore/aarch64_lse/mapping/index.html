detcore::aarch64_lse

Module mapping 

Source
Expand description

Telling code from data in an aarch64 ELF file’s executable sections, by the file’s mapping symbols.

An executable section can hold data as well as instructions: OpenSSL’s generated assembly, for one, keeps its constant tables in .text. Those words decode as instructions as readily as code does, so a scan that reads the whole section finds load/store-exclusive “loops” that never execute, and a rewrite that took one would corrupt the table. The AArch64 ELF ABI marks the boundaries with mapping symbols in the symbol table: $x (or $x.<any>) starts A64 code and $d (or $d.<any>) starts data, each running to the next mapping symbol of the same section (“ELF for the Arm 64-bit Architecture”, section 5.5.4, Mapping symbols). A stripped file has no symbol table and so no mapping symbols, and a section can lack them too.

Where a section has no mapping symbols, the file’s unwind table (.eh_frame) is the evidence instead: each frame description entry (FDE) covers one function’s code, stripped files keep the table for unwinding, and a constant table has no FDE. An FDE covers its whole function, so a table or literal pool placed inside the function is inside it too: under that evidence alone, code is what control reaches from the functions’ entries (reachable_code), less what the code addresses as data, up to the next instruction a branch reaches (data_extents), since a call is taken to return; and a sequence a literal load reaches is refused in any case (literal_targets). Bytes neither marks are not known to be code.

These are pure functions of the file’s bytes, which the rewriter (super::elf) consults before it plans a single sequence.

Functions§

addressed_starts
Where words (at base) address bytes as data, or may: the target of each LDR (literal) and ADR, and of each ADRP with every ADD (immediate) or unsigned-offset load or store that completes it among the eight instructions after it, taking the ADRP’s register as its base, up to the instruction that writes that register without completing it, since the page is gone from there. One ADRP can address several tables. An ADRP nothing completes gives its page, the lowest address it can be completing. Each is where a table may start: how far it runs is not in the instruction (data_extents).
can_return
Whether the function function (its entry and end, as an FDE gives them) can return: walking its own words from its entry, some instruction it reaches is a RET X30, or a direct branch out of it (a tail call) goes to a function that returns says comes back. A RET through another register is not a return to this function’s caller, and an SVC proves nothing past it, whatever its immediate, since what the kernel does with it is not in the file. What this does not check is a write to X30 before a RET X30, so a function that returns somewhere else through a changed link register is taken to return to its caller, and an unresolved BLR, whose callee is unknown, is taken to come back. A function whose entry is outside words is taken to return, which is the ordinary case for a call out of the section. A function whose every path ends in a trap or in a syscall that does not come back (an exit or abort helper) cannot, and a call to it does not fall through.
code_spans
The code of section section, which starts at address and is size bytes long, as address ranges, given symbols sorted as mapping_symbols returns them: each $x to the next mapping symbol of the section, or to its end. Bytes before the section’s first mapping symbol are not code, and a mark outside the section is ignored. None when the section has no mapping symbol, so its code cannot be told from its data.
data_extents
The bytes a function may hold as data, where only the unwind table tells code from data: from each address the code addresses as data (starts, addressed_starts) inside a function (functions, the FDEs’ ranges, sorted) to the next instruction a branch reaches (branches, as direct_branches gives them), or the function’s end. Control does not run into a table, so the code after one is reached by a branch, and only a branch that is not itself inside a table counts: a table word can decode as one. An address at a function’s entry is a pointer to the function, not data. The ranges come back sorted and merged.
direct_branches
Every direct branch of words (at base), as (its address, its target).
fde_ranges
The address range of each FDE of an unwind table (.eh_frame, at address), sorted. None when the table cannot be read to its end: a reader that skipped an FDE it could not decode would take that function’s code for data, which is safe, but one that misread a length could take data for code.
literal_targets
The byte ranges words (at base) load as literals or take the address of: each LDR (literal) target with its load’s size, and each ADR target as one word, since what follows it is not known. A literal pool inside a function is read this way, so a candidate sequence any of these reach is data the unwind table took for code.
mapping_symbols
The mapping symbols of a symbol table, given the string table it names: the local, untyped symbols whose names are $x or $d, sorted by section and address. Where a $x and a $d mark the same address, the $d sorts last and so wins: a word that may be data is not taken for code.
reachable_code
The code among words (at base) that control can reach from entries without leaving covered (sorted, disjoint): following each instruction to the next unless it is an unconditional branch, a return, an indirect jump or a trap, and each direct branch to its target. Under the unwind table alone this is what is taken for code: an FDE covers its whole function, including a constant table the function branches over or keeps after its return, and those bytes are not reached. Code reached only through a jump table or an exception landing pad is not either, and is left alone with them. A call falls through only where returns proves the callee comes back; data_extents takes back what the code addresses as data.
returning_functions
Which of functions (sorted by entry, as the FDEs give them) can return, by can_return over and over until the answer stops growing: a function returns if a RET is reachable in it, and a call it makes comes back only if that callee is already known to return and never does not name it as one that cannot. Each round can only add functions, so a few settle it; the bound keeps a deep chain from costing more than it is worth, and stopping early leaves a function unproven, which is the safe side.
symbol_table
Where an ELF64 little-endian file’s symbol table and the string table it names are, as file ranges (offset, size), from its section header table. None when it has no symbol table (a stripped file) or the table’s string table is not one.
unsupported_mapping_symbols
The local, untyped symbols named like mapping symbols (a $ name) that are neither $x nor $d, with or without a .suffix, as (section index, name), in table order: AArch32’s $a and $t, and any other $ name, such as $xyz or $dx. They are reserved for mapping symbols, so this reader cannot say where they put code or data, and a section that has one is not proved by its mapping symbols: a $a after a $x would otherwise leave the code range running through it.
