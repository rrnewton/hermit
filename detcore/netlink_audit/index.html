Module netlink_audit

Determinize the volatile fields carried by NETLINK_AUDIT status replies, and classify audit request types for write containment.

libaudit (reached from PAM stacks, e.g. inside an rpmbuild guest) exchanges AUDIT_GET for an audit_status reply on a NETLINK_AUDIT raw socket. Nothing flagged audit sockets before this module, so the reply – 232 bytes measured in the pam rebuild under --verify (claude-provrepro p06) – reached the guest byte-for-byte. audit_status carries the host audit subsystem’s LIVE COUNTERS and the host auditd pid (linux/audit.h):

  audit_status field        offset  why it moves
  pid                         12    host auditd's pid: host identity
  lost                        24    records dropped: advances with host load
  backlog                     28    messages queued right now
  backlog_wait_time_actual    40    cumulative seconds of queue-wait

The differing bytes in the observed 232-byte reply were those fields: the two runs saw different backlog (716 vs 196) and lost (112 vs 100) counts.

The volatile fields are ZEROED, the same “freeze, don’t virtualize” choice crate::netlink_route and crate::sock_diag make for their live counters and identities: a guest under Hermit has no deterministic clock or host audit daemon against which advancing host counters would mean anything. Configuration fields (enabled, failure mode, rate and backlog limits, feature bitmap) pass through untouched.

Write containment is judged separately from reads: an AUDIT_SET or AUDIT_USER-class message is an instruction to the host audit subsystem. Whether the host kernel would honour it depends on capabilities the guest happens to hold (measured on this host: the kernel acks -ECONNREFUSED when no audit consumer is registered, and CAP_AUDIT_CONTROL in a child user namespace cannot reach the init namespace’s configuration) – but Detcore must not let that be the only barrier, so typed sends are classified here and mutating types are refused by name at the send entry points.

Known residual, shared with NETLINK_ROUTE/NETLINK_SOCK_DIAG: sockets are flagged when Detcore sees them created, so an audit socket it did not see created (an inherited initial descriptor, or one adopted from outside the guest) is neither sanitized nor write-contained. Descriptors passed inside the guest join the sender’s open-file description and keep the flag.

Functions§

audit_request_mutates
Whether an outgoing netlink message of this type only reads the audit subsystem and so may be sent on to the host kernel. Every other audit-domain type (1000 and above) either mutates host audit configuration (AUDIT_SET and family: rules, TTY/module/logging controls) or emits a record into the host audit log – the kernel’s user-message ranges 1100-1199 (AUDIT_FIRST_USER_MSG..=LAST) and 2100-2999 (..MSG2) are record emission gated only by CAP_AUDIT_WRITE in audit_netlink_ok, and AUDIT_USER_TTY (1124) also drives tty_audit_push(). Unknown and kernel-record types are refused too: new write verbs must not acquire a pass-through by default. Types below 1000 are generic netlink control (NLMSG_*), never audit requests.
audit_send_mutating_type
The first message type in an outgoing NETLINK_AUDIT buffer that would act on the host kernel’s audit subsystem, if any. Walks the buffer the way the kernel does – sequentially by nlmsg_len – so a mutating message cannot hide behind a read-only one; a malformed or truncated tail ends the walk, as it would the kernel’s parse.
audit_sends_mutating_type
The first mutating message type across a batch of datagrams (sendmmsg). Each datagram is classified on its own: the kernel parses every skb independently (nlmsg_ok/nlmsg_next per skb in audit_receive), so concatenating a batch into one buffer would let padding or an overlong header in one datagram hide the next.
sanitize_audit_reply
Zero the volatile audit_status fields in a NETLINK_AUDIT GET reply, in place. Returns whether the buffer was modified.
