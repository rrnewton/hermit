Hermit makes Linux execution repeatable by controlling scheduling, time, and randomness. This scorecard compares its backends: determinism asks whether repeated runs agree, while parity asks whether a backend agrees with the reference ptrace backend. Each cell is one workload, execution mode, and backend; results distinguish passes, failures, and unmeasured cells. Totals may combine qualifying results from multiple runs; rebuilding this website does not rerun the tests. For context, start with the introduction to Hermit, or visit the README for setup and usage.

Measured results still count when a combination is disabled. 0 other cells have no conclusive result and are listed in the data audit. 2,787 + 8,575 + 0 = 11,362 manifest cells.

How determinism is tested. Run the program twice under Hermit. Compare its guest syscall logs, recorded memory checks, outputs and exit status. The recorded details must match. A pass without this log comparison does not count as a determinism match.

Backend comparison. The determinism number of every backend uses the same 598 verify tests. These are the verify tests with a recorded ptrace result, including failures. With partial credit. Full matches earn one point. A diverging run can earn a fraction based on its first differing scheduler turn and the length of a complete ptrace run at the same commit. Parity (measured after determinism)

Parity compares a backend's log with ptrace's after both pass the repeatability check. The compared backends are kvm, liteinst, sabre, dbt, in-guest-trap; their test inputs must match. A full log match scores 1. Otherwise, the score is the matching start of the logs divided by the length of the longer log. Parity has its own denominator: tests selected for ptrace verification, on each candidate backend. Tests without a usable ptrace log, cases with incompatible inputs, and cases omitted from a sampled run are excluded. Disabled, missing or failed candidate results score 0.
