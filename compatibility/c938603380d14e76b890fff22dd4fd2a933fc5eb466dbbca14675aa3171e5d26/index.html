Hermit makes Linux execution repeatable by controlling thread scheduling, clocks, and randomness. This compatibility tracker shows recorded test results. A backend is how Hermit observes and controls a running program. The reference ptrace backend uses Linux's process-tracing interface; it is Hermit's default and best-tested implementation. Backends differ in execution overhead, host requirements, and which programs they support.

Each cell is one test program, mode and backend. A program can contribute several cells: verify checks repeated execution, replay checks recording and replaying a run, and chaos checks repeatability with selected thread-schedule seeds. The native baseline runs directly on Linux, outside Hermit.

Determinism asks whether repeated runs on the same backend agree. Parity asks whether another backend agrees with ptrace. The tables and plots below show these comparisons separately; their explanations state which tests each percentage counts.

Determinism: repeatability within one backend. Run the program twice under Hermit. Compare its guest syscall logs, recorded memory checks, outputs and exit status. The recorded details must match. A pass without this log comparison does not count as a determinism match.

Which tests count. The determinism number of every backend uses the same 0 verify tests. These are the verify tests with a recorded ptrace result, including failures. Replay and chaos are shown in their own columns, each over its own cases (0 replay and 0 chaos), and are not part of the determinism number. Recorded comparisons count even if the combination is no longer enabled. In the full-match column, failures and cases without a matching comparison earn no credit but stay in this shared denominator. The resulting percentage shows how much of this reference test set each backend has passed with matching repeated runs.

0 ptrace test-and-mode cases use a reduced log comparison that omits some recorded details. They are excluded from every determinism denominator because they do not check for a full match.

With partial credit. Full matches earn one point. A diverging run can earn a fraction based on its first differing scheduler turn and the length of a complete ptrace run at the same source revision. Missing measurements earn no credit. The table shows the total points as a decimal, divided by the same reference count. Partial credit describes how far the runs agreed before diverging; it does not turn a failure into a pass.

Parity (measured after determinism)

Parity: agreement with ptrace. A backend can repeat its own behavior yet behave differently from the reference. Parity compares a backend's log with ptrace's after both pass the repeatability check. The compared backends are kvm, liteinst, sabre, dbt, in-guest-trap; their test inputs must match. A full log match scores 1. If the logs diverge, partial credit is the number of matching log entries before the first difference, divided by the number of entries in the longer log. Parity = matching INFO logs; partial credit = matched prefix / longer log. Parity has its own denominator: tests selected for ptrace verification, on each candidate backend. Tests without a usable ptrace log, cases with incompatible inputs, and cases omitted from a sampled run are excluded. Disabled, missing or failed candidate results score 0.
