Architecture

How the suite fits together

agent-utils turns a project's Git checkout into a harness that one person can supervise. This page goes one level below the overview figure: what each layer is responsible for, how one task travels through it, and where its state lives. Every section links to the document that is the authority for it. The repository's own documents also call agent CLIs such as Claude Code and Codex "harnesses"; this site calls those agent CLIs and keeps "harness" for the directory.

Layers and responsibilities

Each layer has one job and a narrow interface to the next. The coordinator talks to subagents only through agentctl and wrkslots, never by typing into terminals directly, and only the coordinator talks to the owner. The colored bar beside each layer's section below is that layer's color in the overview figure.

The owner

You decide what gets done and you own the policy. The coordinator writes launch profiles exactly as you state them and never invents models, flags or permission settings. It must not edit the skills or the harness AGENTS.md unless you ask; when you do ask, it makes the change, records it in AGENTS.md and commits the harness. Widening the herdr-run allowlist is your decision, not an agent's.

Skills and instructions are owner-controlled

The owner channel

The simplest channel is the coordinator's own Herdr tab: attach to it and type. Pause automation with agentctl pause before you type into a terminal a script also writes to.

The chat bridge, agentctl chat, connects one chat space to the coordinator. It accepts messages only from allowlisted senders, stores each one durably, and marks it with a reaction that means "received", not "done". Herdr then pastes the message into the coordinator's pane. The agent replies between two marker lines; the bridge posts each reply to the original thread and retries it under a stable request ID so it is not posted twice.

agentctl's Python and Rust editions have different chat bridges. The Python bridge polls Google Chat's public API, once an hour by default; --interval sets a shorter cycle, down to a fraction of a second, and an operator-supplied event command delivers messages at once. The Rust bridge is an event-driven host for subscription plugins, and no plugin ships yet. Without chat, you use the Herdr tab.

vibe-talk, optional and early, is a separately deployed phone reader for a chat service: one-sentence summaries of long messages, named threads, replies from the phone, and voice. It reads and posts in the chat; it does not start or type into agents. So it reaches the coordinator only if agentctl chat bridges the same chat space, and today that needs a piece you supply: vibe-talk reaches Google Chat only through a Discord-compatible bridge, none of which ships here, and agentctl chat has no Discord or Slack transport without an adapter you write. That combination is not documented or tested. vibe-talk's page shows it in five short clips.

The coordinator

The coordinator is an ordinary coding agent started in the harness root. At the start of every session it reads the harness AGENTS.md and the coordinator skill. Where the two disagree, the harness file wins, and inside the primary checkout that repository's own rules win.

Its priorities are fixed: what you explicitly asked; a red main branch back to green; finishing work in flight; then the backlog. It treats a subagent's blocker as a claim to investigate, and it checks results by content. Setup starts it as the registered agentctl session coordinator, and with chat connected it points the bridge at that session with agentctl chat run; registration is what lets timers, scripts and other agents reach it with agentctl send coordinator. A coordinator started instead with the shorter agentctl chat launch belongs to the bridge's shell instead and is not in agentctl's registry, so agentctl send coordinator, which tick-hub's delivery script uses, does not reach it.

Sessions: agentctl on Herdr

Herdr is a persistent terminal server, installed separately. Every agent runs as its own terminal interface in a Herdr tab, so a person can attach and take over at any time. agentctl and herdr-run each talk to Herdr through their own adapter.

agentctl keeps a registry of named sessions in the harness's private .agentctl/ directory. It needs no hosted account and no always-running manager process. Prompts go through a durable queue. Exit code 75 means a prompt is safely pending and can be retried with agentctl drain. Exit code 76 means it may already have been submitted, so it is set aside for inspection and never resent automatically. agentctl start --slot starts an agent inside a wrkslots slot. agentctl wait reports that an agent is ready for input, which is not the same as finished.

Workspaces: wrkslots

Each task gets a slot: a linked worktree of the primary checkout on a fresh branch, created from the remote-tracking default branch. Where the host allows it (passwordless sudo, or fuse2fs), setup's default keeps each slot in its own sparse ext4 image, so a runaway build fills its own image rather than the disk, and removal deletes one file. Each slot gets its own systemd resource limits. An optional file-system sandbox makes only the slot, its Git directories and named paths writable; it is an accident boundary for cooperative agents, not a security boundary.

wrkslots records ownership in an append-only, hash-linked event history. It removes a slot on one of two paths. Ordinary reclaim needs the slot's time-to-live to have expired, the harness liveness check (bin/agent-liveness, which asks agentctl) to report the agent dead, the exact owner process to be gone, and process, mount, Git and path checks to agree. When the owner instead writes a handoff and releases the slot itself, the coordinator must read that handoff, and the census of processes using the slot and the salvage still run, but the waits for the owner to exit, for the liveness check and for the time-to-live are skipped. Either way, unpublished commits are pushed to a configured salvage remote or kept in a verified local bundle before anything is deleted.

Recurring work: tick-hub

tick-hub decides which reminders and freshness checks are due and prints lines such as HEALTH:, ACTION:, NOTE:, ERROR: and NO_RESULT:; it does not schedule or deliver anything itself. In a harness, a user systemd timer runs a small tick-deliver script every 15 minutes. When a tick's output contains an ACTION: line, the script sends that output to the coordinator's agentctl session with agentctl send, the same queue your own messages use, and a message that has to wait stays queued for the next run.

Validation and landing

The project's own rules decide how work lands: pull requests or direct pushes, required reviews, required checks. The coordinator validates before pushing, never trusts an exit status read after a pipe, and after a push or merge reads the result back from the remote by content. dagrun can run the project's validation graph locally under resource limits. herdr-run runs an allowlisted command, such as git push, when the agent's own sandbox blocks the network. gh-paced paces GitHub calls. pr-landing-planner, which is experimental, can propose a landing order but never acts on it.

A delegated task, end to end

This is the path in the harness AGENTS.md template, with the file-system sandbox off (the default). Placeholders are in angle brackets; $WS is the harness's wrkslots command and $AU its agent-utils bin/.

  1. You ask owner

    In the coordinator's tab or in chat: "Please have a subagent add CONTRIBUTING.md and land it." The coordinator turns the request into a task with a short name, its slug (for example add-contributing), and an explicit write destination: which repository, which slot, which branch, and whether the agent may write.

  2. A fresh slot coordinator · wrkslots

    The coordinator fetches the primary checkout's remote, because a slot starts from the remote-tracking branch, then creates the slot:

    git -C <primary> fetch origin
$WS create <slot> --slot-type agent --coordinator-authorized \
  --agent <name> --task <slug> --purpose "<one line>" \
  --coordinator-pid <pid> --repo <primary>=<primary> \
  --branch <primary>=<name>/<slug>

  3. A subagent with a full brief coordinator · agentctl

    It starts a subagent in the slot with one of your launch profiles and a brief that states the goal and why, the slot and branch, how to validate, how to report back, and the slot protocol:

    AGENTCTL_WRKSLOTS_BIN=$WS $AU/agentctl start <name> --cwd <harness> \
  --profile <profile> --slot <slot> --file <brief>

    The subagent appears as a new tab in the project's Herdr workspace. Every task gets a fresh agent name.

  4. Work in the slot only subagent

    The subagent binds itself as the slot's owner (wrkslots adopt), works and commits only on its branch, and publishes as the project's rules require. It then writes a handoff (what changed, the commit, how it was validated, open questions), releases the slot and replies.

  5. Supervise without guessing coordinator

    agentctl status and agentctl read show progress, and the reply in read is what says the work is finished. A successful start or send proves delivery, not completion. If delivery is uncertain (exit 76), the coordinator looks before it resends.

  6. Verify by content coordinator

    It reads the diff, the test output and the pushed ref, then the handoff ($WS read-handoff). "Tests pass" counts only once it knows which tests ran, on which commit, with what result.

  7. Stop and remove coordinator · wrkslots

    $AU/agentctl stop <name>
$WS remove <slot> --coordinator-pid <pid> --expected-generation <n>

    wrkslots refuses unless it can prove nothing uses the slot, and it salvages any unpublished commits first. A refusal names its reason. Nobody deletes a slot by hand.

  8. Land under the project's rules coordinator

    It validates with the repository's own command, lands as the repository allows, and reads the result back from the remote. In the quickstart run, the coordinator checked the landed file byte for byte against the remote.

  9. Report substance coordinator → owner

    It tells you what changed and why it matters, cites work by issue or pull-request number and slug (#<number> <slug>), and says what it did not verify, along with anything left over, such as a pushed working branch it could delete.

With the sandbox on

A sandboxed subagent cannot write the wrkslots registry, so it does not adopt or release its slot. It replies with its handoff, and the coordinator removes the slot after agentctl stop once the slot's time-to-live has passed.

The harness directory

Setup turns the checkout you started in into the harness root and moves the checkout inside it, unchanged. For a repository foobar:

~/work/foobar/                  harness root; the coordinator runs here
├── AGENTS.md                   you are the coordinator; layout, tools, delegation,
│                               suite configuration, and your project rules
├── CLAUDE.md -> AGENTS.md
├── foobar/                     primary checkout, an independent repository
├── agent-utils/                clone, submodule, or symlink to an existing checkout
│   ├── bin/                    tool dispatchers; Python edition, nothing to build
│   └── skills/
├── worktrees/                  wrkslots control directory
│   ├── slots/<slot>/           one checkout (or disk image) per task
│   └── wrkslots                the wrkslots command for this harness
├── bin/agent-liveness          exit 0 dead, 1 alive, 2 unverifiable
├── .agents/skills/             links into agent-utils/skills/
├── .claude/skills -> ../.agents/skills
├── .agentctl/                  session registry and launch profiles; private
└── .wrkslots.yml               slot policy, commented key by key

The harness is its own small Git repository, local unless you add a remote, so its configuration and rules are versioned. Its .gitignore excludes the primary checkout, agent-utils/, worktrees/, .agentctl/, herdr-run's spool and any chat configuration. agentctl refuses to use launch profiles unless .agentctl/ is ignored.

Skills are linked rather than copied, so updating agent-utils updates every skill. By default setup links four skills: the setup and coordinator skills plus agentctl and wrkslots. It adds the skill of each optional tool you choose. The bin/ dispatchers run the Python edition and print one engine= line on standard error; the Rust edition runs only when you ask for it with DAGRUN_ENGINE=rust, and never as a silent fallback. The name is historical: that variable is one switch for every dispatcher. Under rust, the Python-only tools (wrkslots, wrkviz, parallel-experiment-runner and the older herdr-chat and herdr-subagents names) refuse with exit 127, and the Rust edition is built through Cargo on first use, so set it for one command, not for a whole harness.

Durable decisions do not belong in any of these. The coordinator skill puts defects, findings and landing evidence in the project's issue tracker, pull requests or tracked files, because a terminal pane or a chat thread is not a record.

How the owner stays in the loop

One voice

Only the coordinator speaks to you, on whichever channel you use. Subagents report to it, and it sums up. Its reports describe substance, not activity: which flag, file or test changed and why, with numbers and where they came from.

References you can follow

Work is cited as #<number> <slug>, never a bare number. Text an agent publishes, such as a commit body or an issue comment, says which agent wrote it. "Done" means delivered and checked, and anything unverified is named.

Eyes on every agent

Each agent is a real terminal interface in a Herdr tab. Attach to any of them, read along, or pause automation and type. Nothing hides in a background process.

Policy stays yours

Launch profiles, the herdr-run allowlist, the skills and the harness AGENTS.md change only when you ask. Later changes, such as "turn on the sandbox for subagents", are requests to the coordinator, which records each one.

Boundaries and limits

  • Linux only for the harness tools. wrkslots needs /proc; slot limits, boxes and dagrun need a user systemd manager and cgroup v2; herdr-run needs a systemd user manager. agent-usage also runs on macOS, and Herdr itself also installs there.
  • Not a security boundary. The slot sandbox is "an accident boundary, not a security boundary", the herdr-run allowlist is "a cooperative safety rail", and a chat plugin's process group is for cleanup, not containment. They help cooperative agents avoid mistakes; they do not contain a hostile one.
  • Readiness is not completion. agentctl can tell you an agent is waiting for input and that a prompt was delivered. Only the agent's reply says the task is done.
  • External terminal server. Herdr is a separate project. The suite was last tested with Herdr 0.8.
  • One working chat transport. Google Chat through the Python edition's polling bridge, once an hour by default unless you set a shorter interval, plus operator-supplied adapters. The subscription-plugin protocol has no provider yet.
  • Beta and pre-1.0. agentctl calls itself beta software, and every package version is below 1.0.
