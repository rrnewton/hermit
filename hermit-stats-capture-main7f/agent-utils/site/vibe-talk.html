Optional tool

vibe-talk

optionalearlyRust servicev0.0.1

A small Rust web server and phone web app for reading, discussing and replying to your coding agents' chat messages when you are away from the terminal: one-sentence summaries of long messages, named threads, replies from the phone, read-aloud and voice conversation.

About the clips on this page

They show the real vibe-talk server and page, built from this repository, but no live chat service and no live model. The Google Chat space is a local mock bridge. The summaries and thread names come from a local mock of Anthropic's Messages API that returns hand-written text after a short delay. The project, its agents and its owner are fictional. The tap ripple and the desktop pointer are drawn by the recorder, not by vibe-talk. What is real and what is a stand-in has the details.

Purpose

What it is for

Problem
A team of agents posts long reports, often many before you look, and some of them wait on your answer. On a phone, and especially by ear, you need one line per long message, a way to open one particular message in full, threads you can find again, and a way to reply without a terminal.
What you get
A phone web app with Main, Threads and All views of a channel. One-sentence summaries of long messages and short, stable names for threads. Agent reports drawn the way the chat service draws them, with the agent's tag and title lifted into the row header. Replies and thread posts from the phone, and new messages while the page is open. Read-aloud through the phone's own speech engine or ElevenLabs, and voice conversation with an agent meant to look messages up through vibe-talk's MCP endpoint; the maturity table says how far that has been tested.
Needs
A host to run it, as a native build or a container. Something in front of it that terminates TLS if you expose it; the microphone needs HTTPS. A credential for your chat service. Optionally a model provider for summaries and a voice vendor for conversation. It holds the chat credential, needs no access to any development workspace, and is deliberately not run next to the coding agents.
Where it fits
It is an optional phone front end for a chat service, beside the harness's owner channel rather than part of it. It reads and posts in the chat. It does not start, stop or type into agents, so it reaches a harness's coordinator only if agentctl chat bridges the same chat space. Today that needs a piece you supply: vibe-talk reaches Google Chat only through a Discord-compatible bridge, none of which ships with agent-utils, and agentctl chat has no Discord or Slack transport without an adapter you write. vibe-talk also posts as its own bot, so agentctl chat would have to accept that sender. This combination is not documented or tested.

Summaries of long messages

The channel of a fictional Google Chat space, on a phone. Long agent messages are folded to their first three lines. Tapping Summaries replaces each folded message with a tinted, labeled one-sentence summary, and the view scrolls through the day's plan, a test fix, a feature report and an approval request.

Each summary is one plain Messages API call with no tools, made once per message and then kept. The full message stays one tap away.

New messages while you watch

With the newest messages on screen, worker-1 reports a regression test, and six seconds later the coordinator returns that worker's slot to the pool. Both appear without a reload, through vibe-talk's live stream, and a new chip jumps to them.

Here the mock bridge sends vibe-talk a content-free change hint for each message, so the server reads the bridge at once instead of waiting for its next poll. Live updates need a poll interval, which is off by default; a hint only brings the next read forward.

Answer from your phone

The owner taps Reply on worker-3's request to land a toolchain bump, types "Yes, land it. Thanks!" and sends. The reply appears linked to the request, which is marked as dealt with. Worker-3's "Landed" message arrives pointing back at the reply, and then the coordinator confirms that the day's tasks are done.

The post is vibe-talk's own and reaches the mock bridge. The agents' answers are scripted by the mock: no agent ran.

Threads on a desktop

At desktop width the page can show two columns: Main on the left and, on the right, the threads as cards, each with a generated name, a one-sentence summary, its age and its unread count. Opening csv-export-review shows that thread. The owner replies from the box beside it, and worker-2's answer arrives in the same thread.

A thread's name is chosen once and kept, so you can find it under the name you first learned, as long as vibe-talk has storage configured and the thread does not stay quiet or unread past the summary retention period. Without storage, names last only while the server runs. Its sentence is refreshed as the thread grows.

Provenance

What is real in the clips, and what is a stand-in

The clips were recorded to show the page, not to prove a deployment. Everything on screen is drawn by vibe-talk, but the chat service and the model behind it were local mocks.

Real vibe-talk

  • The server and the page: a release build from this repository, started with an ordinary configuration file.
  • Reading through the bridge contract vibe-talk uses for Google Chat.
  • Summaries, thread names and their cache.
  • Message rendering and rich headers.
  • Threads, replies, posting and "dealt with" marks.
  • Live delivery to the open page.

Stand-ins

  • The chat service: a local mock bridge serving one fictional Google Chat space.
  • The model: a local mock Messages API with hand-written summaries and thread names, answering after 0.8 seconds.
  • The agents: scripted messages, including their answers to the owner's posts.
  • The scenario. vibe-talk reads whatever agents post in a chat service, and here workers post in the owner's space and the owner answers a worker directly. That is not how an agent-utils harness routes the owner's channel: there only the coordinator speaks to you, and agentctl chat sends every message in its space to the coordinator.
  • The tap ripple and the desktop pointer, drawn by the recorder.

Not shown

  • Voice conversation and read-aloud.
  • Search.
  • The thread picker, a native drop-down that a headless browser does not draw.
  • Emoji reactions.
  • A live Discord, Slack or Google Chat deployment.

Maturity

Providers and maturity

vibe-talk is early, at version 0.0.1. Its README keeps a status table of what works and what is stubbed, and this is that table's view of each provider, shortened. The full table is the authority.

What vibe-talk supports, and how far each part has been tested
PieceSupportedState, from vibe-talk's README
DiscordDirectly, through Discord's HTTP API with a dedicated bot.Written and unit-tested; never run against live Discord.
Google ChatThrough a compatible HTTP bridge that speaks Discord's API. You supply the bridge; none ships with agent-utils.Reading has been exercised with real read-only traffic. Posting tests use local fakes.
SlackBuilt in, through a small fixed part of the Slack Web API.The status table has no row for Slack. Its tests run against a local fake Slack server.
Summaries and thread namesOne plain Messages API call each: the Anthropic API, Google Vertex, or a gateway that speaks the Vertex path.Tested against a local mock Messages API only; never run against a live model provider.
Summaries from ElevenLabs insteadWith no model provider configured, the ElevenLabs conversational agent writes them.Never run against live ElevenLabs. With neither configured, long messages show as failed summaries; nothing falls back to truncation.
Read-aloudThe phone's own speech engine, or ElevenLabs.Device speech is a prototype.
Voice conversationElevenLabs by default, or a WebSocket provider that your deployment runs.A real ElevenLabs agent has been reached; in the README's last test it answered but called none of vibe-talk's tools.
TLSNot included. Terminate it in front of the server, or do not expose the server at all.—

Try it

Running it yourself

vibe-talk's quickstart has six steps with exact commands: a Discord bot, the server's two tokens, a build, an optional step that puts it on the internet, an ElevenLabs agent, and a first conversation. It budgets about an hour for all six, and half that if you stop once the server runs. Two steps are first contact with a live vendor. Step 3 has never made an authenticated call to Discord. Step 5, pairing an ElevenLabs agent with vibe-talk, has not been seen working: the quickstart says no one has completed it, and in the README's last test a real agent answered but did not use vibe-talk's tools. The quickstart says all this up front, so a failure there reads as expected rather than as a broken build.

Related work

vibe-talk's related-work comparison looks at hosted products and open-source projects for reaching coding agents by phone and voice. It recommended composing hosted products. The README states the decision plainly: a server is needed either way to hold the chat credential, and this project would rather own that front door than hand it to a vendor.

Reproduce

Recording the clips again

The recorder, the mock bridge, the mock Messages API and the configuration template are in site/demos/vibe-talk/, which is not published with this site. They need a vibe-talk release build, Python with Playwright and its Chromium, and ffmpeg. They need no network and no credentials, and a full run takes about two minutes. From the repository root:

cargo build --release --manifest-path vibe-talk/Cargo.toml
python3 site/demos/vibe-talk/record_demo.py --publish
python3 scripts/check_site.py

The recorder's README lists the ports, the scripted conversation, the encoding, and what is fragile, such as the page selectors the clip scripts depend on.
